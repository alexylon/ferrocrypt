# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```bash
# Workspace (ferrocrypt-lib + ferrocrypt-cli)
cargo build                              # build workspace members
cargo test -- --test-threads=1           # run all workspace tests sequentially
cargo clippy --workspace --all-targets -- -D warnings

# Desktop app (excluded from workspace; run separately)
cd ferrocrypt-desktop && cargo build
cd ferrocrypt-desktop && cargo run       # launch GUI
cd ferrocrypt-desktop && cargo clippy --all-targets -- -D warnings

# Run specific tests
cargo test test_name -- --test-threads=1     # single test by name
cargo test "output_file" -- --test-threads=1 # filter by substring

# Format
./scripts/fmt.sh   # formats all crates including desktop and experiments

# Windows cross-check (for `cfg(target_os = "windows")` / `cfg(not(unix))`
# arms such as the Windows fallback path in `fs/atomic.rs`). Requires
# `rustup target add x86_64-pc-windows-gnu`, which is already installed on
# this machine.
cargo check  --package ferrocrypt --target x86_64-pc-windows-gnu
cargo clippy --package ferrocrypt --target x86_64-pc-windows-gnu --all-targets -- -D warnings

# Static Linux CLI artifacts (for the `*-unknown-linux-musl` release
# builds). Runs in containers, so it works from macOS; the argument
# defaults to x86_64.
./scripts/build_static_cli.sh aarch64
```

Notes:
- For **doc-only changes**, do not run code tests/builds unless the change affects rustdoc rendering or examples.
- The desktop crate is excluded from the workspace, so root-level `cargo test` / `cargo clippy` do not cover it locally. **CI does cover it** via a separate `desktop` job that runs clippy + build + tests on Ubuntu / macOS / Windows on every PR.
- The Windows cross-check only type-checks (no linker), so it is sufficient for verifying `cfg(target_os = "windows")` / `cfg(not(unix))` arms compile. Use it whenever you touch `fs::atomic` or any other branch that varies by platform. No CI job runs it, so it is the only thing standing between a broken Windows arm and a release — which is why it denies warnings like every other clippy command here.
- The static Linux CLI targets cannot be built on macOS: they need a Linux-targeting linker. `./scripts/build_static_cli.sh` builds one in a container, checks that it names no dynamic loader and needs no shared library, and smoke-tests it on Alpine — the same checks `release.yml` applies before a tag ships the binaries. CI runs the workspace suite against both musl targets on every push (`rust.yml`'s `musl` job), so a release never ships a binary the suite has not run on.
- Run the Windows cross-check on its own. A `ferrocrypt-desktop` cargo command running at the same time makes it fail with `unresolved import ferrocrypt_test_support` in `ferrocrypt`'s own test targets, which looks like a real defect but disappears when the command runs alone. Concurrent workspace commands are fine.

## `.notes/` directory

Gitignored scratchpad for helper files the user asks to be created there — typically markdown (current proposal/plan files, side references during a refactor, etc.). Safe to read for context; nothing in `.notes/` ships with the repo. ## Architecture

Repository layout:

- **ferrocrypt-lib** (`ferrocrypt` on crates.io) — core encryption library. All crypto logic lives here.
- **ferrocrypt-cli** — CLI binary (`ferrocrypt`). Thin wrapper calling library functions.
- **ferrocrypt-desktop** — Slint GUI app. Excluded from the Cargo workspace; built separately.

### Canonical specifications

Three shipping documents are the authoritative references:

- **`THREAT_MODEL.md`** — public security boundary, trust assumptions, supported deployment and filesystem profiles, severity, and release-blocking rules.
- **`ferrocrypt-lib/FORMAT.md`** — wire-format spec (`.fcr` byte layout, `private.key` / `public.key` formats, recipient entries, payload stream, TLV grammar).
- **`ferrocrypt-lib/STRUCTURE.md`** — code architecture spec (module layout, single sources of truth, dependency direction, public API shape, decryption security ordering, architectural invariants).

The threat model governs security scope and release classification;
`FORMAT.md` governs stored bytes and format processing; `STRUCTURE.md`
governs architecture and implementation invariants. The "Library Module
Roles" table below, plus the "Encryption Pipeline" / "File Format" / "Key File
Format" sections in this file, are quick at-a-glance references for working
in-code. If a quick reference disagrees with a canonical document, the
canonical document wins.

### Library Module Roles

| Module | Role |
|---|---|
| `lib.rs` | Public re-exports + module wiring: surfaces the `Encryptor` / `Decryptor` value-type API and `generate_key_pair` / `probe_recipient_mode` / `probe_recipient_mode_with_limits` / `default_encrypted_filename` / `validate_*_key_file` from `api.rs`; re-exports `PublicKey` / `PrivateKey`, `Passphrase`, `ProgressEvent`, `UnauthenticatedRecipientMode` (variants `Passphrase` / `PublicKey`), `AuthenticatedRecipientMode` + `AuthenticatedRecipientModeKind`, `MixingPolicy`, `ArchiveLimits`, `HeaderReadLimits`, `KeyReadLimits`. |
| `api.rs` | Public façade. `Encryptor` (`with_passphrase` / `with_public_key` / `with_public_keys` / `save_as` / `archive_limits` / `write`), the typed `Decryptor` enum (`Passphrase(PassphraseDecryptor)` / `PrivateKey(PrivateKeyDecryptor)`) opened via `Decryptor::open` or `Decryptor::open_with_limits` (the latter accepts a [`HeaderReadLimits`] for files whose header / recipient counts / recipient bodies legitimately exceed the conservative defaults), key generation (`generate_key_pair(output_dir, passphrase, on_event)`), recipient-mode probing (`probe_recipient_mode` / `probe_recipient_mode_with_limits` — cheap structural classification, never a security claim), key-file validation. Decrypt success paths construct the sealed `AuthenticatedRecipientMode` for `DecryptOutcome::recipient_mode`. Translates stable public types into internal protocol calls; owns no crypto, MAC, or header bytes. |
| `protocol.rs` | Single source of truth for encryption, decryption, and key-pair generation. Key generation stages and syncs both key files, commits `private.key` before `public.key`, and flushes the output directory after each commit — through the retained directory handle on Linux and macOS, by path elsewhere. Both commits thread that same retained handle into their Unix fallback routes, so the directory that receives a commit is the one the rollbacks and flushes act on; a rollback removes a key file only while it is still the entry this run committed, and the returned error says when the removal could not be confirmed — the entry was replaced, its identity could not be read, or the file still had other names. It retains both committed file handles through the last pre-return path-identity checks, and distinguishes a pre-commit `public.key` failure (roll `private.key` back) from a post-commit failure (preserve both final names rather than leave a public-only pair). The module defines `pub(crate) trait RecipientScheme` for encryption and `pub(crate) trait DecryptionCredential` for decryption. `encrypt` accepts an owned `Vec<R>` recipient list plus `ArchiveLimits` and `HeaderReadLimits` values, and drops the list once every body is wrapped so a scheme-carried credential does not survive the payload stream; it rejects empty lists with `EmptyRecipientList` and incompatible recipient combinations with `IncompatibleRecipients`, then runs the writer-side header-cap and KDF preflights (`preflight_header_write_limits` + `RecipientScheme::validate_for_write`) — all before any filesystem, archive, or KDF work, so no caller can emit a file the same-configured reader rejects. `classify_recipients_within_limits` is the matching reader-side preflight — recipient classification plus the aggregate header-MAC bound — shared by `DecryptSession::open` and `probe_recipient_mode_with_limits` so the two cannot drift. The timing-safe decryption slot loop covers passphrase and X25519 candidates. Recipient schemes return `RecipientBody`; protocol verifies the header MAC as the final acceptance step from FORMAT.md §3.7. `DecryptSession` keeps one opened input file from structural parsing through decryption, including across the private-key unlock. |
| `passphrase.rs` | The public `Passphrase` type: owned zeroizing passphrase text, redacted `Debug`, crate-only read access. Every passphrase-based operation consumes one; the length rule is enforced by the operations, not here. |
| `key/files.rs` | `KeyFileKind::classify` (cheap pub/priv heuristic), `PUBLIC_KEY_FILENAME`, `PRIVATE_KEY_FILENAME`. |
| `key/limits.rs` | `KeyReadLimits` (public, `#[non_exhaustive]`, with `max_recipient_string_chars` / `max_private_key_wrapped_secret_len` builder methods that clamp at the structural maxima). The caps both key readers apply: recipient-string length and `private.key` wrapped-secret length. |
| `recipient/native/x25519.rs` | X25519 body layout, wrap/unwrap, HKDF info string, X25519 keypair generation (`generate_keypair`), `open_x25519_private_key` (binary key-file unlock with FORMAT.md §8 derivation check), `validate_private_key_shape` (re-exported via `fuzz_exports`). |
| `recipient/entry.rs` | `RecipientEntry` framing (`type_name_len(2) || recipient_flags(2) || body_len(4) || type_name || body`), `parse_recipient_entries`, `ENTRY_HEADER_SIZE`, `RECIPIENT_FLAG_CRITICAL`, `RECIPIENT_FLAGS_RESERVED_MASK`. |
| `recipient/name.rs` | Two distinct validators: `validate_type_name_grammar` (`FORMAT.md` §3.3 byte-level grammar; every wire-format reader/writer routes through it) and `validate_external_type_name` (`FORMAT.md` §3.3.1 namespace policy: `/`-required + reserved-native-name rejection — `pub(crate)` until a plugin surface needs it). Plus `is_reserved_native_name` and `TYPE_NAME_MAX_LEN`. |
| `recipient/policy.rs` | `NativeRecipientType` (Argon2id / X25519) registry, `MixingPolicy` (Exclusive / PublicKeyMixable), `enforce_recipient_mixing_policy`, `classify_recipient_mode`, `count_supported_recipients` (how many entries the slot loop may try, used to bound aggregate header-MAC work). |
| `recipient/native/argon2id.rs` | Argon2id body layout, wrap/unwrap, HKDF info string, `validate_body_preflight` (FORMAT.md §3.7 step 8: `kdf_params` against the §2.2 structural bounds, no resource cap — that arrives with the caller's `KdfLimit` and stays in `unwrap`). Adding a new native recipient is a new submodule plus a `NativeRecipientType` variant. |
| `container.rs` | Single source of truth for `.fcr` header build/parse: `HeaderReadLimits` (public, `#[non_exhaustive]`, with `max_header_len` / `max_recipient_count` / `max_recipient_body_len` / `max_header_mac_work_bytes` builder methods that clamp at the structural maxima; the last bounds the product of the first two, which is what a reader hashes when every candidate recipient authenticates the whole header), `ParsedEncryptedHeader`, `BuiltEncryptedHeader`, `read_encrypted_header`, `build_encrypted_header`. Header MAC is computed/verified by `format::compute_header_mac` / `verify_header_mac`; this module includes the MAC tag in the on-disk byte stream and the parsed result, but the caller is responsible for verifying it after a successful recipient unwrap. `write_encrypted_file` retains the finalized file through an immediate pre-return path-identity check, so it never reports an ambient path that no longer names its committed output. |
| `key/private.rs` | `private.key` byte layout (`PrivateKeyHeader`, `PRIVATE_KEY_HEADER_FIXED_SIZE = 90`), `seal_private_key`, `open_private_key`, `OpenedPrivateKey`. Cleartext fields are bound as AEAD AAD; AEAD cannot distinguish wrong-passphrase from tampered-cleartext, both surface as `KeyFileUnlockFailed`. |
| `key/public.rs` | `public.key` Bech32 grammar (`encode_recipient_string`, `decode_recipient_string`, `DecodedRecipient`, `RECIPIENT_STRING_LEN_LOCAL_CAP_DEFAULT`), internal SHA3-256 typed-payload checksum domain-separated from the BIP 173 checksum, fingerprint helper (`fingerprint_hex` over `type_name \|\| key_material`). The public `PublicKey` wrapper stores one `ResolvedPublicKey` (suite + key material) resolved by its constructor, so a fingerprint and a later encryption always describe the same bytes; there is no re-read and no lazy source. |
| `archive/mod.rs` | Module entry point and `IncompleteOutputPolicy` definition. Re-exports `prepare_archive`, `PreparedArchive`, `unarchive`, `validate_encrypt_input`, `ArchiveLimits`, and `IncompleteOutputPolicy`. The one-call `archive` helper is compiled only for tests and the `unstable-fuzzing` feature. |
| `archive/format.rs` | FCA wire-format constants and primitives: header parse/build (`parse_fca_header` / `write_fca_header`), manifest serialize/parse (`serialize_manifest` / `parse_manifest_bytes` / `checked_manifest_len`), big-endian integer helpers, and `copy_exact_n`, which copies an exact number of bytes for both encode and decode. `read_exact_fca` reads declared FCA regions and reports an incomplete authenticated region as `MalformedArchive`, while preserving payload-stream and filesystem I/O error classifications. Per-entry TLV regions are validated through `crypto::tlv::validate_no_known_critical`; FCA archive version `0x01` defines no per-entry TLV tags. Wire constants: `FCA_MAGIC = b"FCA\0"`, `FCA_VERSION = 0x01`, `FCA_HEADER_SIZE = 27`, `FCA_ENTRY_FIXED_SIZE = 18`, `KIND_FILE = 0x01`, `KIND_DIR = 0x02`, `PERMISSION_BITS_MASK = 0o777`. |
| `archive/model.rs` | FCA model types: `FcaHeader` (parsed header summary including `archive_ext_len`), `ArchiveEntryKind` (File / Directory enum), `ArchiveEntry` (path_utf8, mode, size, opaque `entry_ext: Vec<u8>` carrying the per-entry TLV region, plus writer-only `source_path: Option<PathBuf>` and `source_id: Option<(u64, u64)>`), `Manifest` (entries + total_file_bytes + root_name + root_is_file + root_mode). |
| `archive/limits.rs` | `ArchiveLimits` (public, `#[non_exhaustive]`, caps for FCA: entry count, total plaintext bytes, path depth, per-path UTF-8 byte length, serialized manifest byte length, plus extension caps `max_archive_ext_bytes` / `max_entry_ext_bytes` / `max_total_entry_ext_bytes` / `max_tlv_value_bytes`; one `max_*` builder per cap, a published `*_DEFAULT` constant per cap, and `PATH_BYTES_STRUCTURAL_MAX` — the only format-imposed ceiling — which `max_path_bytes` clamps at) plus the shared `enforce_per_entry_caps` / `enforce_total_bytes_cap` helpers — applied symmetrically on encrypt (writer-side preflight) and decrypt (extraction-time gate). |
| `archive/path.rs` | FCA path grammar — the **single shared** writer/reader validator. `validate_fca_path` enforces UTF-8, relative-only, no leading/trailing/repeated `/`, no NUL, no backslash, byte-length cap, depth cap, no `RootDir` / `Prefix` / `CurDir` / `ParentDir` host components. `validate_fca_component` (private) enforces per-component rules: max 244 bytes per component (`FCA_COMPONENT_MAX_BYTES`, leaves room for the `.incomplete` staging suffix under the 255-byte filesystem name limit), no ASCII control bytes including DEL, no C1 controls, no bidirectional span controls (`U+202A..=U+202E`, `U+2066..=U+2069`; the three direction marks are accepted), no line or paragraph separator (`U+2028`, `U+2029`), no Windows-reserved chars (`<>:"|?*`), no trailing dot/space, no Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `CLOCK$`, `CONIN$`, `CONOUT$`, `COM0..9`, `COM¹`/`COM²`/`COM³`, `LPT0..9`, `LPT¹`/`LPT²`/`LPT³`) — including reserved stems with extensions (`CON.txt`, `LPT9.bin`), ASCII-case-insensitive only. `ascii_case_collision_key` lowercases ASCII A–Z and `unicode_form_collision_key` applies that key to the path's NFC form, both for tree-side duplicate detection (used by `tree.rs`). |
| `archive/tree.rs` | FCA manifest tree-shape validator. `validate_manifest_tree` enforces single top-level root, root-file-implies-single-entry, every non-root entry's parent present as a Directory, no child under file path, no exact-duplicate paths, no ASCII-case-insensitive duplicate paths, no Unicode-form (NFC) duplicate paths, declared total-bytes within cap. Order-independent (HashMap-based parent lookup) so non-canonical manifest order still validates per spec §9.8. |
| `archive/encode.rs` | FCA writer: source-tree traversal (metadata pass) + content-streaming pass. Owns `validate_encrypt_input`, the per-entry rule set (reject symlinks, FIFOs, sockets, devices, Windows reparse points), `metadata_perm_mode` (Unix), the `cfg(unix)` / `cfg(windows)` `open_no_follow` symlink guard (other targets are rejected at compile time), the iterative `walk_directory` builder (heap-backed `PendingDir` stack so deeply-nested source trees cannot overflow the process stack), deterministic `sort_entries_canonically` (depth-asc + path bytes per spec §9.8), and the content-pass `stream_source_file` (single-file roots stream from the handle held since the metadata pass; directory descendants reopen no-follow through the held capability; fresh metadata, recorded-identity check on Unix, size-match check, `copy_exact_n` of declared size only). Caps, including the manifest-size cap, apply while the tree is walked. Hardlinks are archived as regular files. Non-Unix platforms use `DEFAULT_FILE_MODE = 0o644` / `DEFAULT_DIR_MODE = 0o755`. |
| `archive/decode.rs` | FCA reader: header + `archive_ext` + manifest parse with full validation, then content extraction via the hardened cap-std platform backend. Owns `unarchive`, `unarchive_inner` (the FORMAT.md §9.11 18-step pipeline; reads `archive_ext_len` bytes after the header and runs `validate_no_known_critical` against them before any output), `extract_single_file_root` and `extract_directory_root` (3-pass: pre-create dirs depth-asc → stream files in manifest order → chmod dirs depth-desc), `apply_root_directory_mode` and `apply_root_file_mode` (post-rename chmod — on Unix, until commit, directory roots remain owner-private and owner-accessible so permissive stored modes cannot expose staged plaintext and restrictive stored modes cannot obstruct failure cleanup; file roots remain owner-private so a permissive stored mode is not briefly visible; both confirm the reopened root against the staged identity via `require_staged_identity` and chmod through that same handle, so a substituted entry never receives the archive-chosen mode; a confirmed identity ratifies the commit (`PromotedIdentity`), keeping failure-path cleanup off the committed output, and an identity that could not be read skips the chmod), `verify_archive_eof` (rejects any trailing byte), `incomplete_working_name`, `StagedRoot` (what the run staged, and its removal) with `StagedIdentity` (the staged object's identity, keeping "no handle held" apart from "the identity is unavailable" — unreadable, or all-zero and so carrying no information; both skip the post-promotion comparison and neither fails the extraction by itself, but only "unavailable" also skips the root-mode application, and a file root whose link count could not be read has already failed before this state), `require_single_linked_file` (the retained-handle `nlink == 1` post-condition every committed file root goes through, before the root mode is applied so a second name is never widened to it), `promote_root` (Linux/macOS handle-relative promotion; Windows/other path-based fallback), `map_already_exists`. Decryption writes under an `.incomplete` working name throughout and promotes to the final name on success (handle-relative on Linux/macOS, path-based on Windows/other targets); on failure the staged tree is removed under the default [`IncompleteOutputPolicy::DeleteOnError`] — restoring first, parents before children, the descendant directory modes Pass 3 applied (`restore_descendant_access` via `platform::restore_owner_access`, by name from each parent, the one route open to a directory left without read permission), and appending to the returned error a removal that failed or could not be confirmed (`CleanupOutcome::report`) with the working path — or left for inspection / recovery under [`IncompleteOutputPolicy::RetainOnError`]. A step-16 identity match ratifies the committed output before step 17 by moving the staged record out of the cleanup slot without closing its handle — a filesystem may renumber an object once its last handle closes, so the handle stays open until the last comparison; subsequent final-name, destination-directory, retained-staging-link, or extra-link errors are report-only and cannot trigger cleanup. The destination-directory confirmation skips only `EMFILE` / `ENFILE` / `ENOMEM` and their Windows counterparts; permission denial and other ordinary failures propagate. A second handle for the staged root is taken before any content is streamed and is required: a run that cannot hold one returns `CryptoError::Io` there, before any plaintext, since without it neither the post-promotion identity comparison nor the plaintext-destroying cleanup can run; it stays open across promotion on every platform — on Windows a directory root's second handle is opened by name with delete sharing so the promotion rename can proceed beside it, and `retain_staged_directory` confirms by identity that it denotes the directory just created before recording it. A directory root is created and then opened by name, so before the first byte of content `require_staged_root_owner` confirms through `platform::compare_owners` that the root reports the same owner as the first file the run created beneath it (two objects one run created agree on every filesystem; a directory another user planted between the two operations does not); a mismatch refuses the run, leaves the entry in place, and drops the staged record, since it is not the run's to remove. Cleanup tracks only the root this run created via `mkdir_strict` / `create_file_at`, chooses the removal from what the run staged rather than from what now occupies the working name (a staged file is emptied through its own handle and unlinked, never removed recursively; a staged directory is removed through its own handle on Unix, by name on Windows and only while the entry at the working name is still the staged directory), and stays anchored to the SAME `cap_std::fs::Dir` opened for extraction, so a path swap of `output_dir` between failed extraction and cleanup cannot redirect the `remove_*` calls. A pre-existing `.incomplete` left over from a previous failed run survives a retry that fails with `Incomplete output already exists`. |
| `archive/platform.rs` | Capability-based extraction primitives built on `cap-std` and `cap-fs-ext`, shared across Linux, macOS, and Windows. Directory opens use `open_dir_nofollow`; Windows also checks `FILE_ATTRIBUTE_REPARSE_POINT` to reject junctions and mount points. `open_file_nofollow` opens without blocking on Unix and requires a regular file, so a substituted FIFO or other special file cannot delay or receive the final permission update. File and directory creation use no-follow, no-clobber operations with restrictive initial permissions. Permissions are applied through open handles; `restore_owner_access` is the one by-name exception, giving the owner back access to a staged directory from its parent handle during failure cleanup, because a directory left without read permission cannot be opened for a change of its own (cap-std's `O_PATH` + `/proc/self/fd` route on Linux, `fchmodat` with `SYMLINK_NOFOLLOW` on every other Unix). Linux and macOS also promote `{root}.incomplete` through the held output-directory handle. `ObjectId` is the identity of a filesystem object read from a handle — `(dev, ino)` on Unix, volume serial number and file index on Windows, through `fs::atomic::file_identity`, which returns none for an all-zero identifier so a filesystem without identifiers makes the comparisons skip rather than confirm — that the extractor compares after promotion; `compare_owners` / `OwnerComparison` says how the owners of a staged directory root and a file created beneath it compare (Unix; unavailable on Windows), which is how the extractor tells its own staged root from one planted between its creation and its open; `retain_staged_dir` is the second handle to a staged directory root held across promotion (a duplicate on Unix; on Windows a fresh by-name open with delete sharing, because a cap-std directory handle would refuse the promotion rename). `PromotionOutcome` records which route committed the final name. Every committed file root goes through the `nlink == 1` count read through the retained staged-file handle, whatever that route was and whether or not the staging name was removed, because a link a local writer made against the staged plaintext survives the promotion. A hard-link fallback needs it for a second reason: an unlink failure is reported without withdrawing the final name, while a nominally successful or missing-name unlink cannot be trusted as cleanup. The path-based file promotion off Linux and macOS is marked the same way on Unix targets, where `tempfile`'s primitive can itself commit by hard link. Directory extraction uses standard per-file syncs plus one handle-relative macOS `F_FULLFSYNC` barrier on the completed staged root before promotion, avoiding one full-device flush per file without weakening the strongest-available durability boundary. |
| `archive/fd_limit.rs` | Test-only (`cfg(test)`, Linux/macOS) open-file-limit control: `NofileLimit` sets the soft `RLIMIT_NOFILE` (never above the hard limit) and restores it on drop; `HeldDescriptors` holds descriptors so a test runs with a known number free. Mutates a process-wide limit, so every test using it is `#[ignore]`d and runs only under the serial `--include-ignored` lanes. |
| `format.rs` | Wire constants and primitives: `MAGIC`, `VERSION`, `Kind` (`KIND_ENCRYPTED = 0x45 'E'`, `KIND_PRIVATE_KEY = 0x4B 'K'`), `PREFIX_SIZE = 12`, `HEADER_FIXED_SIZE = 31`, `HEADER_MAC_SIZE = 32`, structural caps (`HEADER_LEN_MAX`, `RECIPIENT_COUNT_MAX`, `BODY_LEN_MAX`, `EXT_LEN_MAX`) and matching `*_LOCAL_CAP_DEFAULT` resource caps, `Prefix` / `HeaderFixed` parse+build, `compute_header_mac` / `verify_header_mac`. |
| `crypto/keys.rs` | Typed key newtypes (`FileKey`, `PayloadKey`, `HeaderKey`) with `pub(crate)` constructors and narrow `expose()` accessors so the type system enforces "MAC uses HeaderKey, payload uses PayloadKey". File-key generation (`FileKey::generate`), payload/header subkey derivation (`derive_subkeys`, `DerivedSubkeys`), passphrase wrap-key derivation (`derive_passphrase_wrap_key`), `random_bytes` / `random_secret`, key-size constants (`ENCRYPTION_KEY_SIZE`, `FILE_KEY_SIZE`), and the pinned `HKDF_INFO_PAYLOAD` / `HKDF_INFO_HEADER` info strings. |
| `crypto/kdf.rs` | `KdfParams`, `KdfLimit` (public, `#[non_exhaustive]`, with `new` / `from_mib` / `max_time_cost` / `max_lanes` / `max_work` builder methods that clamp at the structural maxima; `max_work` bounds `mem_cost * time_cost`, defaults to the writer's own budget, and is anchored to that fixed constant rather than derived from the memory cap so tightening memory cannot refuse the cheap low-memory/high-pass profiles), Argon2id parameter validation (structural and policy caps), `ARGON2_SALT_SIZE`, `KDF_PARAMS_SIZE`. |
| `crypto/hkdf.rs` | HKDF-SHA3-256 expansion helper (`hkdf_expand_sha3_256`). |
| `crypto/mac.rs` | HMAC-SHA3-256 helpers (`hmac_sha3_256_parts`, `hmac_sha3_256_parts_verify`), constant-time 32-byte compare (`ct_eq_32`), `HMAC_KEY_SIZE`, `HMAC_TAG_SIZE`. |
| `crypto/aead.rs` | XChaCha20-Poly1305 single-shot seal/open helpers (`seal_file_key`, `open_file_key`), `WRAP_NONCE_SIZE`, `TAG_SIZE`, `WRAPPED_FILE_KEY_SIZE`. |
| `crypto/stream.rs` | `EncryptWriter` / `DecryptReader` streaming adapters using 64 KiB chunks, plus `payload_encryptor`, `payload_decryptor`, `BUFFER_SIZE`, and `STREAM_NONCE_SIZE`. Writers follow the deferred-final-chunk rule from FORMAT.md §5; readers use one-byte lookahead and reject an empty final chunk after any non-final chunk. Any returned error is terminal: the adapter drops its cipher state, and later operations return `StateExhausted`. |
| `crypto/tlv.rs` | Shared TLV grammar for all FerroCrypt extension regions: `.fcr` header `ext_bytes`, `private.key` `ext_bytes`, FCA `archive_ext`, FCA per-entry `entry_ext`. ### Encryption Pipeline

```
Input file/dir
  → archive::prepare_archive() validates and records the source tree
    before cipher work or output staging, retaining the source handle
  → generate random 32-byte file_key + 19-byte stream_nonce
  → derive payload_key + header_key from file_key (HKDF-SHA3-256)
  → for each recipient: wrap file_key into a recipient body
       argon2id: passphrase → Argon2id → HKDF → wrap_key → seal file_key
       x25519:   ECDH(ephemeral, recipient_public_key_bytes) → HKDF → wrap_key → seal file_key
  → build header (prefix(12) || header_fixed(31) || recipient_entries(N) || ext_bytes)
  → HMAC-SHA3-256 over (prefix || header_fixed || recipient_entries || ext_bytes)
    with header_key → header_mac(32)
  → write prefix || header || header_mac to the staged .fcr file
  → PreparedArchive::write_to() writes the FCA payload (header + manifest +
    file content) and streams it through EncryptWriter<File> applying
    XChaCha20-Poly1305 STREAM-BE32 directly to disk, keyed by payload_key
```

No plaintext intermediate files touch disk. The FCA payload is never materialized — its header + manifest + file-content region stream directly through the encryption layer. The `EncryptWriter` defers committing a full chunk until either more plaintext arrives (then `encrypt_next`) or `finish()` is called (then `encrypt_last`), so a non-empty plaintext whose length is an exact multiple of 65,536 ends with a full-size FINAL chunk, not a stray empty trailer (`FORMAT.md` §5).

Decryption reverses (`FORMAT.md` §3.7 acceptance order):

1. read + structurally validate the header (`container::read_encrypted_header`); local caps enforced before any allocation.
2. `recipient::classify_recipient_mode` — reject unknown-critical entries and native entries with non-zero flags, a wrong body length, or a failing per-type body preflight (`argon2id` KDF params outside the FORMAT.md §2.2 bounds; `x25519` all-zero or non-canonical ephemeral), then enforce `argon2id` exclusivity (all before any KDF or private-key unlock).
3. `HeaderReadLimits::enforce_header_mac_work` — reject a file whose supported recipient count times its header size exceeds the aggregate cap, still before any private-key unlock. Steps 2 and 3 together are `protocol::classify_recipients_within_limits`, which both `DecryptSession::open` and `probe_recipient_mode_with_limits` call, so probe and decrypt cannot disagree.
4. iterate supported recipient slots in declared order:
    - flags-zero / body-len backstop (the classify preflight already validated shape);
    - per-recipient `unwrap` (Argon2id for `argon2id`, ECDH for `x25519`);
    - on success, derive `payload_key + header_key` from the candidate `file_key`;
    - `format::verify_header_mac` is the FINAL acceptance gate (per-candidate failure → `HeaderMacFailedAfterUnwrap { type_name }`, loop continues).
5. validate TLV `ext_bytes` (`common::validate_tlv`) AFTER MAC verify, so the validator operates on authenticated bytes.
6. `DecryptReader` streams ciphertext through XChaCha20-Poly1305 STREAM-BE32, peek-ahead resolves "exact-N final chunk" vs "exact-N then more data"; `archive::unarchive` parses the FCA header, reads `manifest_len` bytes for the manifest, fully validates it (per-entry shape, path grammar, tree shape, total-bytes equality), then streams file content via `copy_exact_n` and verifies archive EOF.

A candidate that unwraps but fails the header MAC surfaces as `HeaderTampered` (passphrase) or `HeaderMacFailedAfterUnwrap` (public-key); a credential that opens no supported slot surfaces as `RecipientUnwrapFailed`, and `NoSupportedRecipient` is reserved for a file with no supported recipient type.

### File Format (every artefact)

See `ferrocrypt-lib/FORMAT.md` for the full byte-level spec. Summary:

**`.fcr` 12-byte plain prefix at offset 0:**
`magic(4) "FCR\0" || version(1)=0x01 || kind(1)=0x45 'E' || prefix_flags(2) || header_len(4)`

- `kind = 0x45 'E'` for any encrypted file. The symmetric-vs-hybrid distinction is **not** in the prefix; it's derived from the recipient list (one `argon2id` entry → Symmetric; one or more supported `x25519` entries → Hybrid).
- `prefix_flags` MUST be zero; non-zero rejects as `MalformedHeader`.
- `header_len <= HEADER_LEN_MAX` (16 MiB structural). Local resource cap (`HEADER_LEN_LOCAL_CAP_DEFAULT`, 1 MiB) rejects oversized declarations as `HeaderLenCapExceeded` before allocation.

**Header layout (right after the prefix):**

```
header_fixed(31) || recipient_entries(recipient_entries_len bytes)
                || ext_bytes(ext_len bytes) || header_mac(32)
```

`header_fixed = header_flags(2) || recipient_count(2) || recipient_entries_len(4) || ext_len(4) || stream_nonce(19)`. HMAC-SHA3-256 with `header_key` authenticates `prefix(12) || header_fixed || recipient_entries || ext_bytes` (32-byte tag = `header_mac`). Forward compatibility: ignorable TLV tags in `ext_bytes` are authenticated + skipped; critical tags (`0x8001..=0xFFFF`) are rejected as `UnknownCriticalTag`. See `FORMAT.md` §6.

**Recipient entry framing** (`FORMAT.md` §3.5):

```
recipient_entry = type_name_len(2) || recipient_flags(2) || body_len(4)
                  || type_name (UTF-8, validated against §3.3 grammar)
                  || body (opaque to framing; per-recipient module parses it)
```

`recipient_flags` defines bit 0 as `critical`; all other bits MUST be zero.

**Native recipient bodies** (two native types ship today):

- `argon2id` (116 B): `argon2_salt(32) || kdf_params(12) || wrap_nonce(24) || wrapped_file_key(48)`. `MixingPolicy::Exclusive` — must appear alone.
- `x25519` (104 B): `ephemeral_public_key_bytes(32) || wrap_nonce(24) || wrapped_file_key(48)`. `MixingPolicy::PublicKeyMixable` — multiple `x25519` slots allowed in one file (decrypt iterates).

**File-key indirection:** every recipient body seals the same per-file random 32-byte `file_key`. After unwrap, `payload_key` and `header_key` are derived from `file_key` via HKDF-SHA3-256 (`info = "ferrocrypt/v1/payload"` with salt = `stream_nonce`; `info = "ferrocrypt/v1/header"` with empty salt). Identical post-unwrap shape across recipient types; future native types (post-quantum, hybrid KEMs) plug in as new `RecipientEntry` `type_name`s without touching the header-MAC scope or the payload pipeline.

**Payload (`FORMAT.md` §5):** XChaCha20-Poly1305 STREAM-BE32 over 64 KiB plaintext chunks. Writers MUST NOT emit an empty trailing chunk after non-empty plaintext that ends on a 65,536-byte boundary; the final non-empty chunk uses `last_flag = 1`. Empty plaintext is encoded as a single tag-only `last` chunk.

### Key File Format

**`public.key`** is a **UTF-8 text file** containing exactly one line: the canonical lowercase `fcr1…` Bech32 recipient string, optionally followed by a single trailing LF (any other surrounding whitespace rejects as `MalformedPublicKey`). The Bech32 payload carries a typed body `public_key_version(1) || type_name_len(2) || key_material_len(4) || type_name || key_material` plus an internal 16-byte SHA3-256 checksum (in addition to the BIP 173 checksum), domain-separated so cross-algorithm collisions are impossible. For X25519 the file is 109 bytes on disk: 108 recipient-string characters plus the trailing LF. Identity verification is out-of-band via the SHA3-256 fingerprint of `type_name || 0x00 || key_material`.

**`private.key`** (176 bytes for X25519 with `ext_len = 0`):
- Cleartext fixed header (90 B): `magic(4) || version(1) || kind(1)=0x4B 'K' || key_flags(2) || type_name_len(2) || public_len(4) || ext_len(4) || wrapped_secret_len(4) || argon2_salt(32) || kdf_params(12) || wrap_nonce(24)`
- Variable fields (right after the fixed header): `type_name(type_name_len) || public_material(public_len) || ext_bytes(ext_len)`
- Wrapped secret (`wrapped_secret_len` bytes): `secret_material(secret_len) || Poly1305_tag(16)`
- Every cleartext byte before `wrapped_secret` is bound as AEAD **associated data**, so tampering any cleartext field fails authentication. AEAD cannot distinguish "wrong passphrase" from "tampered cleartext" — both surface as `CryptoError::KeyFileUnlockFailed` with wording `"Private key unlock failed: wrong passphrase or modified key file"`.
- Wrap-key derivation: `HKDF-SHA3-256(salt=argon2_salt, ikm=Argon2id(passphrase, argon2_salt, kdf_params), info="ferrocrypt/v1/private-key/wrap", L=32)`.
- `kind = 0x4B` ('K') is deliberately distinct from the encrypted-file `kind = 0x45` ('E') so `file(1)`-style matchers and the in-tree `KeyFileKind::classify` heuristic can disambiguate `private.key` from `.fcr` on a single byte.
- The `type_name` field is the recipient discriminator (no separate algorithm byte). `"x25519"` ships today; future native key kinds (post-quantum, hybrid KEMs) extend the `type_name` set without touching the header layout.
- Forward compatibility: TLV tags in `ext_bytes` are authenticated via AEAD-AAD. Validated after successful AEAD unwrap.

## Key Conventions

- Operation API: the public surface is `Encryptor` / `Decryptor` value types in `api.rs`, plus the free function `generate_key_pair(output_dir, passphrase, on_event)`. Encrypt is built via `Encryptor::with_passphrase(Passphrase)` / `with_public_key(PublicKey)` / `with_public_keys(IntoIterator<Item = PublicKey>)`, optionally chained with `.save_as(path)` / `.archive_limits(limits)`, and finalized with `.write(input, output_dir, on_event)`. Decrypt opens via `Decryptor::open(input)` (or `Decryptor::open_with_limits(input, HeaderReadLimits)` for files that exceed the conservative default header / recipient-count / recipient-body caps) which classifies the file's recipient list (no crypto, no KDF) and returns the matching `Decryptor::Passphrase(PassphraseDecryptor)` or `Decryptor::PrivateKey(PrivateKeyDecryptor)`; each variant takes `.kdf_limit(KdfLimit)` / `.archive_limits(ArchiveLimits)` / `.header_read_limits(HeaderReadLimits)` / `.incomplete_output_policy(IncompleteOutputPolicy)` and `.decrypt(credentials, output_dir, on_event)`; `PrivateKeyDecryptor` also takes `.key_read_limits(KeyReadLimits)` for a `private.key` whose wrapped secret exceeds the default cap. A successful decrypt returns `DecryptOutcome { output_path, recipient_mode: AuthenticatedRecipientMode }`, where the sealed `AuthenticatedRecipientMode` is constructed only by the decrypt path (recipient unwrap + header MAC verify) and so is unforgeable from caller code. The `IncompleteOutputPolicy` defaults to `DeleteOnError` (a failure removes this run's `.incomplete` plaintext while the output is still treated as staged, restoring the directory modes the run applied first and reporting a removal that failed or could not be confirmed in the returned error; a later filesystem error preserves an output already confirmed as complete); `RetainOnError` keeps staged output for backup-recovery / forensic flows but the caller MUST treat retained partials as potentially attacker-chosen prefixes (STREAM-BE32 truncation caveat). Multi-recipient encrypt is part of the public API: `Encryptor::with_public_keys([alice, bob])` produces a single `.fcr` either recipient can decrypt. `UnauthenticatedRecipientMode` (`Passphrase` / `PublicKey`) is the cheap mode-probe enum returned by `probe_recipient_mode` (or `probe_recipient_mode_with_limits` for elevated caps) for callers that want to pre-classify a file without going through `Decryptor::open`; **its name carries the warning that this is structural classification, not authentication** — the type cannot be passed where an `AuthenticatedRecipientMode` is expected, and the docstring spells out the negatives (no KDF, no MAC verify, no payload decrypt, single bounded header parse on one file handle). All public types are `#[non_exhaustive]` except the two deliberately closed ones: `KdfParams` (public fields mirror the frozen 12-byte wire encoding) and `AuthenticatedRecipientMode` (sealed by its private field). A public `#[non_exhaustive]` type derives `Copy` only where a stated, caller-facing purpose closes its payload space to `Copy`-compatible data — not merely where today's fields happen to be `Copy`. `Copy` narrows the `#[non_exhaustive]` promise, because a later variant or field carrying an owned payload then needs `Copy` removed, and `cargo semver-checks` treats both adding and removing a `Copy` impl as a major change. Every such type states its position next to the derive. Keeping `Copy`: `FormatDefect` (pattern-matchable without heap-allocated `String`s), `UnsupportedVersion` and `InvalidKdfParams` (one wire byte or number per variant), `UnauthenticatedRecipientMode` / `AuthenticatedRecipientModeKind` (categorical, no data), and the four limit structs `ArchiveLimits` / `HeaderReadLimits` / `KeyReadLimits` / `KdfLimit` (a cap is a numeric bound). Not `Copy`: `ProgressEvent`, `IncompleteOutputPolicy`, and `MixingPolicy`, none of which has a closed payload space. The remaining public `#[non_exhaustive]` types — the operation builders, the key and credential wrappers, the outcome structs, `Decryptor`, and `CryptoError` — hold owned data and could not be `Copy` in any case, so they carry no such note. A derived `Eq` carries the same kind of promise: `ProgressEvent` and the three outcome structs state next to the derive that later fields and variant payloads stay `Eq`-comparable (quantities are integers, never floating-point), because removing `Eq` after release is a major change too.
- Key-source abstractions: `Encryptor::with_public_key(s)` consumes `PublicKey`; `PrivateKeyDecryptor::decrypt` consumes `PrivateKey`. `PublicKey` has constructors `from_key_file(path)`, `from_key_file_with_limits(path, KeyReadLimits)`, `from_x25519_bytes([u8; 32])`, `from_recipient_string("fcr1…")` (plus `FromStr`), `from_recipient_string_with_limits("fcr1…", KeyReadLimits)`, and methods `fingerprint()`, `to_recipient_string()`, `to_x25519_bytes()`. Every constructor resolves its source and returns `Result`, so the value holds key material rather than a locator — construction is the only validation point, and there is no `validate()` method. `PrivateKey` has `from_key_file(path, Passphrase)` today; it binds the unlock passphrase at construction, so a future source that unlocks differently fits the same `decrypt` signature. Its `into_key_file_parts` hands the passphrase to the decrypt path by value so it can be dropped right after the unlock, and `protocol::decrypt_session` takes the decrypt credential by value and drops it when the recipient slot loop ends — no reusable secret stays resident during payload extraction. The writing paths follow the same rule: `protocol::encrypt` drops its owned recipient list once every body is wrapped (which is why `PassphraseRecipient` owns its `Passphrase` rather than borrowing one), and `protocol::generate_key_pair` takes its passphrase by value and drops it once `private.key` is sealed, before either key file reaches disk. Both wrappers are `#[non_exhaustive]` structs over private inner state — a resolved key for `PublicKey`, a source enum for `PrivateKey` — so new sources (in-memory secret material, hardware-backed keys) can be added as constructors without breaking the API.
- Progress signalling: `ProgressEvent` is a `#[non_exhaustive]` enum with 5 current variants. KDF events fire at the **actual KDF call boundary** (after structural / resource-cap validation, immediately before the Argon2id call) — never speculatively from the orchestrator. `DerivingPassphraseWrapKey` is emitted from inside `recipient::native::argon2id::wrap`/`unwrap` (passphrase encrypt + decrypt). `UnlockingPrivateKey` is emitted from inside `key::private::open_private_key` (today: public-key decrypt; any future caller that unlocks `private.key` with its passphrase). The other three are `Encrypting`, `Decrypting`, `GeneratingKeyPair` (the last covers the entire keygen flow including its internal Argon2id seal — no nested KDF event there). All variants have `Display` wording locked by a unit test; CLI and desktop render `{event}` directly. Pure-X25519 encrypt and structurally-malformed file rejects fire **zero** KDF events. New progress phases are added as new variants — match arms in caller code need a `_` wildcard.
- **In-repo direction routing:** ferrocrypt-cli and ferrocrypt-desktop call `probe_recipient_mode` (CLI) or read `mode` from UI state (desktop) first, then build the appropriate explicit config. The library no longer exposes auto-routing convenience wrappers — direction detection is a caller concern.
- Bech32 `fcr1…` recipient strings are the human-readable public-key exchange format. The typed entry point is `PublicKey::from_recipient_string(&str)` or `"fcr1…".parse::<PublicKey>()` (see the key-source abstractions bullet above); `decode_x25519_recipient_string(&str) -> [u8; 32]` is kept as the low-level primitive for the `fuzz_recipient_decode` fuzz target and callers that specifically want raw bytes.
- CLI `hybrid --recipient / -r` accepts a `fcr1...` string directly for encryption. `recipient` (alias `rc`) subcommand prints the string from a key file.
- CLI never accepts passphrases as command-line arguments. Passphrases are prompted interactively via `rpassword` (hidden TTY input) with confirmation on encrypt/keygen. For non-interactive use (tests, scripts), set the `FERROCRYPT_PASSPHRASE` environment variable.
- Integration tests use `tests/workspace/` (and `tests/workspace_fixture_stability/`, `tests/workspace_api/`, `tests/workspace_concurrency/`, `tests/workspace_memory_bounds/`, `tests/workspace_roundtrip_randomized/`, `tests/workspace_config_symmetry/`) as temp directories; every binary stages under a per-process `run-<pid>` subdirectory (`ferrocrypt_test_support::per_process_workspace`), so two concurrent `cargo test` invocations cannot delete each other's staged files, and each process removes its own subtree via `#[ctor::dtor]` hooks. `scripts/run_all_tests.sh` and `scripts/run_all_tests.ps1` also prune numeric `run-<pid>` directories whose process no longer exists, so an interrupted test run does not leave permanent workspace litter. The `tests/common/mod.rs` shim exposes `passphrase_auto` / `recipient_auto` / `generate_key_pair` (auto-routing wrappers, plus test-fast Argon2id parameters via `ferrocrypt-test-support`) over the public `Encryptor` / `Decryptor` API so integration test call sites stay compact. Its three stated gaps are recorded on the test: the post-promotion replacement window is covered end to end by `a_post_ratification_replacement_preserves_the_committed_output`, resource exhaustion uses the fd-limit harness, and a staged descendant directory renamed out of the staged root leaves cleanup unable to reach what was written inside it. Writer/reader configuration symmetry lives in `tests/config_symmetry.rs`, which measures each cap that has both halves from both sides and requires the two thresholds to be the same number: the five `ArchiveLimits` caps a writer can exercise, the four `HeaderReadLimits` caps, and the four `KdfLimit` caps on both artefacts that store key-derivation parameters — a passphrase `.fcr` and a generated `private.key`, whose reader is the unlock. Thresholds are searched, not written down, so the suite cannot disagree with the implementation about how an entry, a component, or a header byte is counted, only about whether the two sides agree; it also pins that a refused write leaves the output directory empty, drives recipient counts across the default cap with the decrypting key placed in a slot that is never the first, and asserts the Argon2id write floor as the one boundary the writers apply alone (`KdfBelowWriteFloor`), the reader half of which is covered by the frozen sub-floor fixture in `tests/frozen_fixture_compat.rs`. The four FCA extension caps have no writer half — every current writer emits an empty region — so `archive/decode.rs` drives them as reader boundaries instead, each admitted at exactly its cap and refused one byte under, through a real extraction rather than the enforcement helper. Each of the four limits modules carries a completeness pin: a `#[test]` that destructures its own struct field by field, so adding a cap stops the build on a test whose documentation says where to route it. Filesystem-lane coverage lives in `tests/archive_fs_matrix.rs` (all `#[ignore = "fs-matrix"]`, run by the CI build job and the fs-matrix lanes): besides the round-trip smoke tests, it asserts that a finished decrypt leaves the output directory holding only its output — compared against the whole directory, so a leftover under any name is caught — and that a decrypt cut partway through a multi-chunk payload honours both `IncompleteOutputPolicy` values against a *populated* staged tree. The residue test first probes the two primitives the commit routes are chosen from (atomic no-replace rename, hard link) and names the route in its output and in its failure messages, so a lane's result says which route it exercised rather than leaving it to be guessed; the lane invocations pass `--nocapture` so that line reaches the log. The encryption window between `prepare_archive` and `write_to` is covered generatively by `src/archive/encode.rs::tests::interference_between_the_two_passes_follows_the_rule_for_its_position`, which enumerates position (root file, root directory, descendant) × interference (replaced by a same-length or longer file, a directory, a symlink, a FIFO; moved aside; grown; truncated) and asserts the contract FORMAT.md §9.10 states for each position rather than one uniform rule: a root file and a root directory are reached through handles held since the metadata pass, so nothing done to their path can redirect the content pass, while a descendant is reopened by name and every interference reaches it, and every one is refused: the no-follow, type, and length checks catch all but the same-length regular swap, and on Unix the identity the metadata pass recorded catches that one. Off Unix a directory listing carries no identity to record, so that swap is admitted there, which is what §9.10 requires of a platform exposing none. On Windows a source directory cannot be renamed or removed at all while a preparation holds it open, so those cases assert that platform refusal instead. Randomized round-trip coverage lives in `tests/roundtrip_randomized.rs` (a dependency-free seeded PRNG drives many random payload sizes and contents — including the chunk boundary — and random directory trees through one batched encrypt/decrypt, asserting content, structure, and Unix mode bits survive). The committed `testvectors/suite/` edge-case corpus (FORMAT.md §12) is replayed through the public API by `tests/testvector_suite.rs`; it is regenerated by the ignored `src/suite_vector_gen.rs` test and committed by hand.
- Hard-link fallback races are pinned at both layers. `src/fs/atomic.rs::tests::finalize_via_link_rejects_a_renamed_staging_link_after_not_found` and `finalize_via_link_rejects_a_hidden_link_when_replacement_unlink_succeeds` cover encrypted/key-file commits; `src/archive/platform.rs::tests::a_renamed_staged_link_keeps_the_link_count_check_after_not_found` preserves the archive route marker; and `src/archive/decode.rs::tests::extraction_rejects_a_hidden_link_after_nominal_staging_cleanup` proves the real decrypt caller rejects an extra plaintext link without applying `DeleteOnError` to the committed inode.
- `ENCRYPTED_EXTENSION` (`"fcr"`) is re-exported from `format.rs`.

## Non-Negotiable Rules

- Use idiomatic Rust and repository naming conventions.
- Keep code DRY and focused.
- Avoid magic strings and numbers.
- **Comments.** Non-doc comments (`//`) MUST be tight and earn their place: no unnecessary words, no restating what the code already says, plain international English, no jargon. If the comment only paraphrases the line beneath it, delete it. Doc comments (`///`, `//!`, rustdoc) MUST be professional and crystal clear — they are the public contract a reader sees in the API surface and on docs.rs, so explain purpose, invariants, error conditions, and any non-obvious caller obligations precisely and without hand-waving.
- Do not leave `unwrap()` or `expect()` in normal code paths.
- Never invent cryptography.
- Use standard, reviewed crypto crates and constructions only.
- Treat all external input as adversarial.
- Never leak secrets through logs, errors, debug output, or UI.
- Prefer authenticated encryption.
- Fail closed on malformed, truncated, ambiguous, or unsupported input.
- **Encrypt/archive/encode is fully symmetric with decrypt/unarchive/decode.** Never write a `.fcr` (or its inner FCA archive, or any other on-disk artefact) that the matching reader path would refuse under the same configuration. The writer MUST run every cap, grammar, structural, and policy check the reader runs, before any cipher work. "Wrote it but cannot read it back" is always a writer bug — fix the writer, do not relax the reader.
- **Public-key encryption is fully symmetric with private-key decryption.** Never change key-pair specs so a release accepts a public key for encryption but cannot decrypt with the matching private key (or the reverse). Key-pair suite versions live in their own domain (FORMAT.md §11); the `public.key` parser and the `private.key` parser MUST refuse a removed suite together, and a new suite MUST be wired through both halves before any user-facing release. "Encrypted to a recipient I can no longer decrypt" is always a release bug — fix both parsers, never silently extend support on one side.
- **Resource caps and validation limits are centralized.** Every cap (entry count, total bytes, depth, path bytes, KDF memory, recipient count, TLV value bytes, archive- and per-entry extension bytes, manifest size, etc.) lives in one named constant or `*Limits` struct field. Validation sites read the named source; never duplicate the value as a literal. Adding a new cap means adding a field to the relevant `Limits` struct, a published `*_DEFAULT` constant for it, and a builder method that clamps at a published `*_STRUCTURAL_MAX` wherever the wire format imposes one — not sprinkling new literals across the codebase. Clamping in the builder is preferred over a runtime self-check, because it prevents safe downstream code from constructing a cap the format cannot represent rather than rejecting that cap once an operation has started. Any in-crate access to the `pub(crate)` fields must preserve the same invariant. This is what makes encrypt/decrypt symmetry mechanically enforceable.
- Use strong types where possible.
- Prefer concise user-facing messages; desktop UI space is limited.
- Keep explanations concise and written for humans in your replies: plain language, short, clear, no needless jargon, don't be verbose. Use analogies when they help, skip ceremony, do not pad with restated context.
- Use international English in your replies. Avoid regional idioms (whether American or British), clever shorthand, and compressed phrases; prefer wording that a non-native English reader can understand on the first read. This applies to chat replies, commit messages, code comments, documentation, and error messages.
- Keep parsing, validation, crypto, and I/O separated.
- Add or update important tests and keep them self-contained.
- Add regression tests for security-sensitive and format bugs.
- Every file commit MUST require `nlink == 1` through a retained handle to the committed inode before success, whatever route committed it, because a link a local writer made against the staged file survives the commit. A hard-link fallback MUST NOT infer cleanup from an unlink return value either: a missing staging name, an unlinked replacement, an unreadable count, or any additional link fails after commit without withdrawing the final name. On the decrypt side that count MUST be read before the archive's mode is applied, so a second name is never widened to it, and a wrong count MUST be reported only after the checks that tell a commit of the run's own from a substituted entry — reporting it in their place preserves plaintext the run never committed.
- Prefer fixing issues directly rather than merely documenting them.
- After each important change, but only when we are ready to commit, update if relevant:
    - `README.md`
    - `CHANGELOG.md` under `[Unreleased]` — **strictly user-facing** and held to the same writing standard as comments above: tight, plain international English, no jargon, professional and crystal clear. NEVER describe internal mechanics, private types, helper-function names, refactor moves, test scaffolding, or filesystem-call sequences — those belong in code comments, STRUCTURE.md, or the audit doc, not in CHANGELOG. Public API names and spec terms (`CryptoError` variants, `FORMAT.md` sections, types from the `pub use` surface) are fair game; internal symbols (`cap_std::fs::Dir`, private helpers, file-internal function names) are not.
