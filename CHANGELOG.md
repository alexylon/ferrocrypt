# Changelog

All notable changes to FerroCrypt are documented in this file.

## [Unreleased]

### Added
- **`PrivateKey::into_public_key` returns the public key corresponding to a `private.key` file.** This makes it possible to recover the `fcr1…` recipient string or fingerprint without keeping the matching `public.key`. The method consumes the private key and unlocks it with the passphrase bound at construction, returning a `PublicKey` for `fingerprint()` or `to_recipient_string()`. Unlocking performs the same key derivation as decryption, takes roughly as long, and reports `UnlockingPrivateKey` progress while it runs.

## [0.3.0-rc.4] - 2026-08-22

### Added
- **FerroCrypt now publishes its security boundary and release standard in `THREAT_MODEL.md`.** The document defines what FerroCrypt protects, the output-directory trust requirement, the supported filesystem set, interactive and service profiles, explicit non-goals, severity, and which confirmed security defects block a stable release.
- **`encrypt` and `decrypt` gain `--max-archive-entries`, `--max-archive-size`, `--max-archive-path-depth`, `--max-archive-path-bytes`, and `--max-archive-manifest`.** The caps on the folder inside a `.fcr` file were reachable only from the library, so a folder holding more than 250,000 files and directories, or more than 64 GiB of content, could not be encrypted from the command line at all — and the rejection gave no flag to raise. Both sides apply the same caps, so raising one for a large folder means passing the same flag to the matching `decrypt`. The defaults are unchanged and `--help` prints them.
- **`KeyGenOutcome` now carries the generated key's `recipient_string`.** Getting the `fcr1…` string to hand out previously meant reading `public.key` back, which is a second look at a file that can change in between — so the fingerprint you verified out of band said nothing about the string you published. The string is now returned alongside the fingerprint, both derived from the key material the same call generated. `ferrocrypt keygen` prints the pair from that one source.
- **`HeaderReadLimits` now implements `PartialEq` and `Eq`.** The other limit types — `ArchiveLimits`, `KeyReadLimits`, and `KdfLimit` — already supported equality comparison; `HeaderReadLimits` was the only one that did not.
- **`FCR_FILE_V1_VERSION` pins the first `.fcr` outer-container version byte (`0x01`).** `FCR_FILE_VERSION` is now documented as the byte the current writer emits, matching the existing `PRIVATE_KEY_VERSION` / `PRIVATE_KEY_V1_VERSION` and `PUBLIC_KEY_VERSION` / `PUBLIC_KEY_V1_VERSION` pairs. Code that means "is this a first-revision file" should compare against the pinned constant, so it keeps working the day a future release advances the writer's byte. Both constants equal `0x01` today; no behavior changed.
- **Statically linked Linux CLI binaries for 64-bit Intel/AMD and ARM.** `ferrocrypt-cli-x86_64-unknown-linux-musl.tar.gz` and `ferrocrypt-cli-aarch64-unknown-linux-musl.tar.gz` carry everything they need, so one file runs on any Linux machine of that processor family without a matching C library installed — Alpine, minimal container images, and distributions too old for the existing `gnu` binary. ARM Linux had no published binary at all before. The existing `gnu` binary is unchanged and remains the usual choice on mainstream distributions. The full test suite runs against both new targets before a release ships them.

### Changed
- **Archive paths can no longer contain invisible characters that change how a name is displayed.** A file name may carry Unicode text-direction controls — the characters behind the "Trojan Source" attacks — that make a terminal or file manager show its letters in a different order than they are stored, so that a script named `holiday`, `U+202E`, `gpj.sh` is shown as `holidayhs.jpg`, an image. Encryption and decryption now refuse any archive path containing one of the nine controls that govern a whole span of text (`U+202A`–`U+202E`, `U+2066`–`U+2069`), the line and paragraph separators `U+2028` and `U+2029`, which would show one name as two lines, the DEL byte, or a C1 control character (`U+0080`–`U+009F`), with "contains a control, text-direction, or line-break character" naming the entry. The three direction marks `U+061C`, `U+200E`, and `U+200F` stay accepted: word processors leave them in mixed Hebrew and Arabic names, they cannot reverse a name's letters, and error messages show them escaped. Ordinary Arabic, Hebrew, and other right-to-left names are unaffected: they carry their direction in the letters themselves. This is decided before the stable format is frozen so that every file valid for stable 0.3.0 stays valid afterwards. `FORMAT.md` §9.6 lists the full set.
- **The desktop status bar now wraps a long error instead of cutting it off.** A rejected archive path was always cut before the path itself, so the message never said which entry was refused. The bar now grows upward into the free space above it when there is room; where there is none, it stays one line as before. Desktop only; no library behavior changed.
- **A folder reached twice while encrypting is now refused by what was found, not by a guess at the cause.** The message said "Directory cycle in archive source", which is right when a folder contains itself but wrong when the same folder simply sits at two places in the tree — what a bind mount does. It now reads "Directory reached twice in archive source". The folder is refused either way, as before, because its content would otherwise be archived twice.
- **On Linux and macOS, writing an encrypted file is now bound to the folder the write started in, even if that folder's path changes during the write.** FerroCrypt opens and retains the output folder before it creates the staged temporary, then finalizes through that same handle. If the folder is renamed or replaced during encryption, the substituted folder receives nothing. When the staged file remains in the original folder, FerroCrypt commits it there and reports that the requested path no longer names the output; if a local process moves the staged file out of that folder, FerroCrypt refuses the commit. An older release could instead complete into the replacement folder. Decryption has worked this way for some time; encryption now matches it. On Linux and macOS, the handle asks the system for only what a commit uses — placing and removing entries inside the folder, never listing it — so an output folder you can write to and enter but not list still works. Key generation keeps its existing readable-folder requirement, which its durability step needs. On other targets the final commit remains path-based; Unix filesystems that cannot finalize a file in one step still use the readable-folder fallback, and Windows keeps its existing atomic no-replace move.
- **An archive can no longer contain two paths that differ only in Unicode spelling.** The same visible name can be written in two byte forms — `é` as one composed character, or as `e` plus a combining accent — and a case-sensitive filesystem can hold both files at once, typically after unpacking a Mac-made archive on Linux. Encrypting such a folder used to succeed, and the decrypt then failed midway on macOS, whose filesystems treat the two spellings as one name. Both encryption and decryption now reject the pair up front on every platform with "duplicate entry differing only in Unicode form", naming the entry. Names are still stored and restored byte-exact; only the duplicate check normalizes. Two names that differ only in letter case beyond ASCII (`Ärzte.txt` and `ärzte.txt`) remain accepted and still fail closed at decryption on filesystems that ignore that difference.
- **Decrypting a folder on macOS is now many times faster without weakening its pre-promotion durability barrier.** Every extracted file was flushed all the way through the drive's own write cache before the folder was renamed to its final name, once per file. On one Apple-silicon machine a 40,000-file folder took 124 seconds, nearly all of it in those flushes; the same folder now takes 6 seconds. FerroCrypt now applies standard `fsync` to each staged file, then issues one `F_FULLFSYNC` for the completed staged tree before promotion. This reduces the expensive full-device barriers from one per file to one per folder while retaining the previous best-effort protection against operating-system crashes and power loss. A single-file decrypt still receives one full flush. Filesystems that do not support the stronger operation fall back to standard `fsync`, as they did before. Linux and Windows are unaffected, and encrypted `.fcr` output and generated key files keep their existing strongest-available flush.
- **`FORMAT.md` now explicitly requires a decrypted root's stored mode to be applied only after final promotion.** Until commit, a Unix reader must keep a directory root owner-private and owner-accessible, preventing a permissive stored mode from exposing staged plaintext and a restrictive one from obstructing failure cleanup; a file root must likewise keep its restrictive initial mode. FerroCrypt already follows this ordering, so no behavior changed. The old explanation instead attributed the ordering to a macOS rename limitation that does not exist.
- **`FORMAT.md` §3.3 now pins which diagnostic a reader reports for a recipient entry that breaks more than one rule.** FerroCrypt has always checked each entry in one fixed order — the 8-byte entry header, the length-field ranges, reserved flag bits, fit inside the declared region, the local body cap, then the type-name grammar — taking entries in declared order, but the specification left that order unstated, so two conforming implementations could report different diagnostic classes for the same bytes. The order is now normative, and §3.7 states that the reserved-flag rejection runs inside the entry parse. FerroCrypt's own behavior is unchanged.
- **The "Incomplete output already exists" message now shows the output folder the same way as "Output already exists".** The whole path was previously escaped and shortened as untrusted text, so a long output folder, or one with non-ASCII letters, was hard to read. The folder now stays readable, and only the staging entry's name, which the archive chooses, is escaped.
- **`ArchiveLimits` now has the same shape as the other limit types.** Each builder method is named after the cap it sets — `max_entry_count(n)` in place of `with_max_entry_count(n)`, and the same for all nine caps. Every cap has a published default (`ArchiveLimits::ENTRY_COUNT_DEFAULT` and its siblings), so raising one cap relative to the defaults no longer means copying a number out of `FORMAT.md` §9.12. `max_path_bytes` clamps at the new `ArchiveLimits::PATH_BYTES_STRUCTURAL_MAX` (65,535, the largest value the stored path length can hold) instead of accepting a larger value and failing once an operation had started; the "Archive path byte limit exceeds FCA u16 path length" error is gone. The fields are no longer public, and the type gained `PartialEq` and `Eq`. Every cap value and default is unchanged — update call sites by dropping the `with_` prefix.
- **`decode_recipient_string` is renamed to `decode_x25519_recipient_string`.** The function has always accepted only native X25519 recipient strings and returns exactly 32 bytes of key material, so the old name promised a generality it can never gain — recipient strings of a future key type will be larger and go through `PublicKey::from_recipient_string` instead. Only the name changed; validation and errors are identical.
- **`KdfLimit` now has the same shape as the other limit types.** Construct with `KdfLimit::new` or `KdfLimit::from_mib`, tighten with `max_time_cost` / `max_lanes` / `max_work`, and compare whole values with `==` — update call sites by dropping the `with_` prefix. Each builder now clamps at the matching published maximum (`KdfLimit::MEM_COST_KIB_STRUCTURAL_MAX` and its siblings), so a cap above what `FORMAT.md` §2.2 can represent is reduced to that maximum instead of being stored as given; two limits that behave the same now compare equal. The fields are no longer public, which lets a future release add a limit dimension without breaking callers. Apart from the new work cap described below, which headers are accepted is unchanged, as are the caps and defaults.
- **`ProgressEvent`, `IncompleteOutputPolicy`, and `MixingPolicy` no longer implement `Copy`.** All three are non-exhaustive so future releases can add richer progress variants, recovery policies, and recipient mixing rules, and some of those may need to carry data that `Copy` forbids — a destination directory for retained partial output, for example. Keeping `Copy` would have turned such an addition into a breaking change later. Progress callbacks already receive events by reference, the policy is passed by value once per decrypt, and a mixing policy arrives inside an error, so most code is unaffected; code that duplicated a value with `*event` or an implicit copy should call `.clone()` instead. `Clone`, `PartialEq`, and `Eq` are unchanged on all three, as is `Default` on `IncompleteOutputPolicy`.
- **`PublicKey::from_key_file` now reads the key file immediately and returns a `Result`, and `PublicKey::validate` is gone.** A file-backed public key used to store only the path and read it again on every use, so taking a fingerprint and later encrypting were two separate reads of a file that could change in between. A `PublicKey` now holds the key material resolved when it was built, which is what makes a fingerprint check binding: the value you verified is the value that encrypts. Add `?` where you build one from a file — a read or parse failure that used to surface at the first method call now surfaces at construction. `validate` had nothing left to check, because a `PublicKey` cannot exist unless its source parsed; use `validate_public_key_file` to check a file without keeping the key. `from_recipient_string` and `from_x25519_bytes` are unchanged.
- **`PublicKey::from_bytes` and `PublicKey::to_bytes` are renamed to `from_x25519_bytes` and `to_x25519_bytes`.** Both methods handle exactly 32 bytes of X25519 key material, so the old names promised a generality they can never gain — a future key type will carry material of a different size and add its own constructors and accessors, while `from_recipient_string`, `from_key_file`, `fingerprint`, and `to_recipient_string` remain the algorithm-neutral surface. Only the names changed; validation, errors, and the returned bytes are identical.
- **Passphrases are now passed as FerroCrypt's own `Passphrase` type, and the `secrecy` re-export is gone.** `Encryptor::with_passphrase`, both decrypt operations, `KeyPairGenerator::with_passphrase`, and `generate_key_pair` previously took `secrecy::SecretString`, which tied the public API to the exact `secrecy` version FerroCrypt shipped with — a breaking release of that crate would have forced a breaking release of FerroCrypt. `Passphrase::new` accepts a `String` or `&str`; the stored text is wiped from memory when the value drops, debug output prints `Passphrase(<redacted>)`, and the text cannot be read back through the public API. Unlike `SecretString`, `Passphrase` does not implement `Clone`, so an operation cannot be handed a copy of a credential another operation already holds: build one value per operation, reading the text from its source each time rather than keeping it in an ordinary `String` that is never wiped. Replace `SecretString::from(text)` with `Passphrase::new(text)` and drop `use ferrocrypt::secrecy::...` imports.
- **The `fuzzing` Cargo feature is renamed to `unstable-fuzzing`.** The feature exists only to give the fuzz harness in the FerroCrypt repository access to internal parsers, and its items may change in any release. The old name did not say so, so build tools and compatibility checkers treated the feature as part of the supported API. Features prefixed `unstable-` are outside the crate's compatibility guarantee, and the module the feature enables no longer appears in the rendered documentation. Code that enabled `fuzzing` must enable `unstable-fuzzing` instead.
- **`PrivateKey::from_key_file` now takes the unlock passphrase, and `PrivateKeyDecryptor::decrypt` no longer has a passphrase parameter.** `PrivateKey` is meant to gain sources beyond the passphrase-protected `private.key` file — in-memory secret material, hardware-backed keys — and those sources unlock differently. With a passphrase fixed in the decrypt signature, every such source would have needed a placeholder passphrase or a second decrypt method. The key value now carries everything needed to use it, so a new source arrives as a new constructor while `decrypt` keeps its signature. Because it holds the passphrase, `PrivateKey` no longer implements `Clone`; build a fresh value for each decrypt. Move the passphrase argument from `decrypt` into `PrivateKey::from_key_file`.

### Fixed
- **A failed decrypt no longer removes an entry another local process placed at the output name (Linux and macOS).** On a drive or network share that cannot finalize in one step — exFAT, some network and FUSE mounts, and every folder decrypt on them — FerroCrypt reserves the output name by creating an empty entry there and then moves the finished output over it. If that move failed, the reservation was removed by name, so an entry that a local process with write access to your output folder had planted in its place was deleted instead of the reservation. FerroCrypt now leaves whatever is at the output name in place — its own empty reservation, or an entry placed there since — because checking which it is and then removing it are two steps, and an entry substituted between them would be the one removed. The name is reported in the returned error, which does not claim whose the entry is, because it may block a retry until you remove it. Encrypted-file and key-file writes follow the same rule; `FORMAT.md` §9.11 now states it normatively.
- **A failed key generation no longer leaves behind the temporary file it staged for `public.key`.** Key generation stages both key files under temporary names and commits `private.key` first. When it failed after `private.key` had reached its final name, the staged public file was removed by its path, so a local process that renamed or replaced your output folder in that moment sent the removal into the replacement folder while the temporary file stayed in the folder the keys were written to. That removal now goes through the folder handle key generation opened before it staged anything, and takes place only while the entry is still the file it staged; one it cannot confirm is named in the returned error. A failure before `private.key` is committed is unchanged.
- **A failed decrypt no longer leaves the complete decrypted folder on disk when the archive holds a read-only folder.** A decrypt writes under a temporary `.incomplete` name and, by default, removes that copy if anything fails before the final rename. Folder permissions from the archive are applied before that rename, and a folder stored without owner write permission — `r-x` folders are common in extracted release trees and reference data — left the copy's contents impossible to delete. Any later failure, such as the output name becoming occupied during a long run, then reported an error while the whole decrypted tree stayed behind at the predictable `.incomplete` path, and every retry failed with "Incomplete output already exists" until the folder was fixed by hand. The removal now first restores FerroCrypt's own permission changes, so a failed decrypt leaves nothing behind whatever the archive declared. Windows is unaffected, as it applies no such permissions.
- **A folder decrypt now stops when its staging folder is found to belong to another user (Linux and macOS).** FerroCrypt creates the temporary `.incomplete` folder and then opens it by name, two steps between which a local process able to write to your output folder could replace it with a folder of its own, which FerroCrypt would then fill with the decrypted files and rename to your chosen name — while that process could read, list, and change them. Before writing any content, FerroCrypt now confirms that the staging folder has the same owner as the first file it created inside it; on a mismatch the decrypt stops with "Incomplete output belongs to another owner and was left in place", naming the folder, and nothing is removed, because the folder is not FerroCrypt's. The comparison is between two objects FerroCrypt itself created, so removable media and network shares that report a fixed owner for everything are unaffected. Windows reports no owner this way and is unchanged; as before, choose an output folder that only you can modify.
- **Two zero file identifiers are no longer taken as proof that an entry is the one FerroCrypt wrote.** FerroCrypt compares the identifier a filesystem assigns each file or folder to check, after a commit, that the entry at a name is still its own. A few network shares and unusual mounts assign none and report zero for everything, so two zeros always compared equal and a replaced entry passed as confirmed: a decrypt would then apply the archive's permissions to it, and a cleanup would remove it. On such a filesystem FerroCrypt now treats a zero as no information: confirmations that only check are skipped, a decrypted output keeps its restrictive staged permissions instead of receiving the archive's, and a removal that depends on the confirmation — a failed decrypt's staging folder on Windows, a key-generation rollback — is reported in the error instead of performed, so on Windows a failed folder decrypt there leaves its incomplete folder, decrypted content included, for you to remove. ext4, APFS, and NTFS always assign real identifiers and are unaffected.
- **A decrypt now says when it could not remove its incomplete output.** When the removal fails for a reason outside FerroCrypt's control — the output folder made read-only by another process, a storage error — the error used to be the original failure alone, which read as if nothing had been written. It now also names the incomplete output and says whether it may still hold plaintext — a single decrypted file is emptied before the removal is attempted, so one that could not be removed holds none — so that the copy is not overlooked. Where the original failure cannot carry the extra text — a tampering or truncation rejection — the call returns `CryptoError::Io` with both messages, so a caller matching on the error type sees `Io` in those cases.
- **The `IncompleteOutputPolicy` documentation described post-commit checks as Unix-only.** The checks that a decrypted output is still the entry FerroCrypt wrote, that it is still in the directory it was written to, and that a decrypted file carries a single name all run on every supported platform. A caller on Windows or macOS could read the old text as meaning those errors cannot reach them, and treat any decrypt error as proof that nothing was written, when complete decrypted content may be on disk under the final name.
- **A failed encrypt or key generation now says when an empty file may be left at the output name (Unix).** On filesystems that offer neither a rename that refuses to overwrite nor hard links, FerroCrypt first claims the output name with an empty file and then moves the finished content over it. If that move fails and the empty file cannot be confirmed as removed, the error now says so, because a further attempt would otherwise be refused with "already exists".
- **Encrypting a folder now refuses a file inside it that was replaced mid-run (Unix).** FerroCrypt reads a folder twice: once to record every name, size, and permission, then again to copy the contents. It already refused a file whose size or type changed in between, but a replacement of exactly the same size passed unnoticed, and the new content was archived under the original name and permissions. This is reachable without an attacker: saving a file in most editors replaces it rather than changing it in place. FerroCrypt now notes which file it recorded and refuses with "Source file was replaced while archiving", naming the file and saying that encrypting again will archive what is there now. The file you point at was already protected this way; this extends it to the files inside a folder. Windows is unchanged — it does not supply the needed identity without opening every file — and keeps its existing checks on links, type, and size.
- **A decrypt no longer reports success when the decrypted file has a second name.** FerroCrypt writes a decrypt under a temporary name and renames it to your chosen name. A local process able to write to your output folder could give that temporary name a hard link of its own, which survives the rename: the decrypted content then sits under a name that process chose, keeps whatever permissions the encrypted file recorded, and stays on disk after you delete the output you were told about. The check that catches this ran only on the drives where FerroCrypt itself commits by hard link. It now runs for every single-file decrypt on every platform, matching what encryption and key generation already required, and reports the extra name rather than hiding it. Where the output is confirmed as the one FerroCrypt wrote, it is left in place and you remove the second name yourself; where the entry at your chosen name turns out to be another process's, the decrypted content is removed instead and the error says the output was replaced. A decrypted folder is not counted this way, so nothing there changes. The check also runs before the permissions recorded in the encrypted file are applied, so a second name is never given those permissions on the way to the refusal. The message for this condition now reports the number of names found rather than naming a cause it cannot know, and reads "Output report.pdf is complete, but has 2 filesystem names (expected 1)" on encryption, decryption, and key generation alike.
- **A decrypt whose staged folders are changed underneath it now stops instead of quietly repairing them.** FerroCrypt creates every folder an encrypted file declares before it writes any content into them. While writing that content it walked to each folder by name, and re-created any that had gone. A local process able to write to your output folder could move one aside after files had been written into it, and the run would make an empty replacement, put the remaining files there, and report success for an output missing everything written before the move. The walk now only opens folders that are already there, so such a change fails the decrypt with "Directory in extraction path went missing", naming the folder, instead of reporting success. Whatever is still inside the staged folder is then removed or kept according to the chosen incomplete-output policy; anything moved out of it is beyond FerroCrypt's reach and stays where it was put, which is why the output folder has to be one only you can modify.
- **Encryption, decryption, and key generation no longer report success when a hard-link fallback leaves another name for the completed file.** FerroCrypt previously hid a failed temporary-name removal for encrypted and key files, while a decrypt could remove a final entry another local writer placed during the delay. Merely accepting a successful or missing-name result was also insufficient: another process with access to the output folder could move the temporary link, or replace it so FerroCrypt removed the wrong entry. After cleanup, the operation now verifies that exactly one filesystem link remains. The check also covers the commit performed inside the platform file library, which on some mounts — Linux network and FUSE filesystems among them — links the file itself without reporting how its cleanup went. Otherwise it reports a post-commit error without withdrawing the final name; inspect the complete final output and any temporary or moved second name manually. On Windows, where the commit itself never links, the same check catches a hard link another local process created against the temporary file before it was committed.
- **Encryption and key generation now reject an output path that was replaced during the operation.** If a local process replaces the final entry or renames and replaces the output folder, FerroCrypt returns an error rather than handing the caller a path to unrelated bytes. A final entry that has disappeared by then is reported the same way, matching how decryption treats its output. FerroCrypt leaves the replacement untouched. If the original file or folder was moved rather than deleted, the complete output remains under its new name; otherwise the error does not promise that it can still be recovered. On affected Linux and macOS filesystems, the durability update also stays with the original folder instead of following its old path to a replacement.
- **A post-decrypt destination check no longer accepts an unreadable replacement folder.** A local writer could replace the output folder with an unreadable directory and make FerroCrypt return a path into that replacement. Only running out of open files or memory can now skip this final check. Permission denial and other ordinary failures are reported, and FerroCrypt does not delete an output it has already confirmed as complete.
- **A passphrase file whose stored key-derivation settings are out of range is now refused before you are asked for the passphrase.** Every `.fcr` file records the settings used to turn a passphrase into a key. A file whose settings are outside the range the format permits — zero parallelism, or a memory or time cost above the maximum — was reported as a passphrase file by `Decryptor::open` and `probe_recipient_mode`, and only failed once the passphrase had been collected and handed to the decrypt call. Both now refuse it at that first step, with the same `CryptoError::InvalidKdfParams` they raised before, alongside the wrong-length and malformed-recipient checks they already performed there. Nothing that decrypted before stops decrypting: the settings were always validated before any key derivation ran, so no such file could ever be opened. Code that matches on the result of `Decryptor::open` or `probe_recipient_mode` should expect `InvalidKdfParams` where it previously saw a passphrase file that failed later.
- **A file with many recipients can no longer demand disproportionate work from the reader.** Every recipient that yields a key verifies the whole file header, so the cost of trying them is the recipient count multiplied by the header size, not the sum. The caps on recipient count and header size each bounded one of those factors, leaving the product free: raising either — which a caller does to handle files with more recipients than the defaults allow — raised the cost quadratically, and at the format's own maxima a 16 MiB file could demand about 64 GiB of hashing. Anyone who knows a recipient's public key can build such a file without being able to read it, so an unattended service that raised the caps and accepted files from strangers could be kept busy by a small upload. The new `HeaderReadLimits::max_header_mac_work_bytes` bounds the product, and a file above it is refused with `CryptoError::HeaderMacWorkCapExceeded` before the private key is unlocked and before any hashing starts. Its default is the most work the recipient-count and header-length defaults could already demand together, so nothing that worked at the default settings changes. Encryption applies the same cap to the recipient list before writing, so a file FerroCrypt writes stays one it can read back. Both factors count, so raising either one far enough means raising this cap on both sides as well: past roughly 750 recipients at the default header size, or past a 1 MiB header at a few dozen recipients.
- **A recipient list longer than a file could ever hold is now refused before it is built.** `Encryptor::with_public_keys` accepts any sequence of public keys, and it used to read the whole sequence into memory, checking the count only once `write` was called. A `.fcr` file holds at most 4,096 recipients, so a longer list could never produce a file at all — yet twenty million entries still cost 610 MiB of memory before the refusal, and a sequence with no end never returned. Collection now stops one entry past that ceiling and returns `CryptoError::RecipientCountCapExceeded`. Lists of 4,096 or fewer are unaffected, and the separate default cap of 64 still applies at `write`, so raising it through `Encryptor::header_read_limits` works exactly as before.
- **A passphrase file can no longer ask for more key-derivation work than FerroCrypt itself produces.** Every passphrase-protected `.fcr` file and every `private.key` stores the memory and the number of passes used to turn a passphrase into a key, and a reader must do that work before it can tell whether the file is genuine at all. Memory was capped at 1 GiB by default, but the pass count was left at the format maximum of 12, so a small file could order three times the work of an ordinary one — about six seconds instead of two on a current laptop — while holding the same 1 GiB for that whole time. The new `KdfLimit::max_work` bounds memory multiplied by passes, defaulting to what FerroCrypt writes at its own settings, and a file above it is refused with `CryptoError::KdfWorkCapExceeded` before any derivation starts; `decrypt` gains `--max-kdf-work` to raise it. Settings that trade memory for passes are unaffected, 64 MiB at 12 passes among them, and the memory cap still applies separately, because a single-pass 2 GiB file is quick but holds twice the memory. Files written at FerroCrypt's default settings are unaffected. The desktop app keeps the wider acceptance of earlier releases: its decrypt raises the work budget to what the 1 GiB memory cap already admits at the maximum pass count, so a file the previous desktop version decrypted still decrypts there. The budget applies when writing too, so that FerroCrypt never produces a file it would then refuse: settings above it, reachable only by overriding `Encryptor::kdf_params` or `KeyPairGenerator::kdf_params` and never from the command line or the desktop app, now fail at `write` with the same error. To use them, raise `max_work` on a `KdfLimit` and pass it to both `kdf_limit` on the writing side and the decryptor on the reading side.
- **An input path of `.` or `..` can now be encrypted.** `ferrocrypt encrypt -i .` failed with "Cannot get directory name", because neither path spells out a name of its own. Both now take the name of the directory they point at, so encrypting a folder from inside it produces the same file as naming that folder from outside. Every other input keeps the name as typed, symbolic links included. The filesystem root, which has no name at all, is still refused.
- **Encrypting to, or generating a key pair on, a network share no longer fails when the operating system interrupts the final flush.** Where a filesystem does not support the stronger flush — the macOS SMB client among them — FerroCrypt uses the standard flush instead, and an interruption during that flush was reported as a failure rather than being retried. Key generation treats a flush failure as fatal and undoes the commit, so an interrupted run left no usable key pair. The staged-folder flush during a folder decrypt was skipped in the same situation and is now retried as well. Filesystems that accept the stronger flush, APFS and exFAT among them, never took that path.
- **The permissions of a folder inside a decrypted folder now reach the disk with its contents.** The permissions stored in the archive were applied to every folder below the decrypted one, but were not written to disk along with the files, so an operating-system crash or power loss in the moments after a folder decrypt finished could leave such a folder at the owner-only permissions used while it was being written (`0o700`) instead of the permissions it was encrypted with. File permissions were never affected, and no file content was ever at risk. Windows is unaffected (no Unix mode semantics).
- **`validate_public_key_file` now judges a key file against the format's own limits, matching `validate_private_key_file`.** A `public.key` whose recipient string is longer than the default reading cap — possible only for key types with more material than X25519 — was reported as too long instead of by what the file actually is, such as a valid key of an unsupported type. Reading keys for encryption is unchanged and keeps the default cap.
- **Encrypting a file that is replaced while the operation starts now fails instead of encrypting the replacement.** FerroCrypt inspects what the input path points at and then opens it. On Linux and macOS it now confirms that the opened file is the one it inspected, so a file exchanged in that short window — at the path itself or through a folder above it — is refused with "Input file changed while archiving". Folder inputs already had this protection. Windows keeps its existing checks, which catch every substitution except a replacement by another ordinary file.
- **Decrypting a file onto a drive that cannot rename in one step no longer passes through a placeholder.** Filesystems whose driver refuses an atomic no-replace rename — Apple's exFAT driver, some network shares — made FerroCrypt reserve the final name with an empty entry and then rename the finished file over it. A local process able to write to your output folder could remove that reservation in the moment it existed and put an entry of its own there, which the rename then destroyed. A decrypted file is now linked to its final name instead, which the operating system refuses just as atomically if the name is taken, so no reservation exists to take over. Decrypted folders, and drives without hard links, keep the reservation step and its documented window.
- **A decrypt that finishes into an entry it did not write now fails instead of reporting success.** FerroCrypt writes a decrypt under a staging name and renames it to your chosen name at the end. Both the rename and the reported path go by name, so a local process able to write to your output folder could put an entry of its own under the staging name, or rename the output folder itself, and the decrypt would report success for something it never wrote. The run now confirms, before reporting success, that the finished name is the entry it staged and that your output folder is still the one the entry was written into; a mismatch reports "Output was replaced while decrypting". Where the folder itself moved, the decrypted output is complete inside it and only the path FerroCrypt would report has stopped leading there, so that case names the output instead: "Output report.pdf is complete but its directory changed". A file created by any of these means is left where it is, never reported as your decrypted output. On Windows, where the final rename goes by path, this also covers a link on that path re-pointed at another folder during the decrypt: the entry renamed there is never reported as your output.
- **A decrypt that runs out of file handles now stops instead of finishing with a weakened check.** FerroCrypt writes a decrypt under a staging name and, before reporting success, confirms that the finished entry is the one it wrote — the check that catches a local process putting its own entry in your output's place. That confirmation needs a handle to the staged entry, held from the moment it is created. A process with no file handles left could not hold one, and the decrypt continued without it: the confirmation was passed over, and the permissions stored in the archive could be applied to an entry FerroCrypt had not written. The handle is now taken before any content is written, and a decrypt that cannot take one stops there and reports "Cannot hold a handle to the staged output". No plaintext is written in that case; the empty staging entry is removed or kept according to the chosen incomplete-output policy, as any other failure before promotion. This applies on every platform, so a Windows decrypt under file-handle exhaustion now stops where it previously ran to completion.
- **A decrypt that ends with its output gone now fails instead of reporting success.** Before reporting success, FerroCrypt confirms that the finished name is the entry it wrote. If a local process removed or renamed the finished output in the moment after it was committed, that name held nothing, the check was passed over, and the decrypt reported success for a path that no longer existed. A name that has gone is now treated the same as a name holding something else, and reports "Output was replaced while decrypting".
- **A decrypt no longer applies the permissions stored in an encrypted file to an entry it did not write.** FerroCrypt writes a decrypt under a staging name, renames it to your chosen name, and then applies the permissions recorded when the file was encrypted. That last step went by name, so a local process able to write to your output folder could put an entry of its own under the staging name and have the sender's chosen permissions applied to it — and because permissions belong to a file rather than to a name, a hard link carried the change to a file anywhere on the same drive, including one outside your output folder. A `private.key` readable only by you could be made readable and writable by everyone. FerroCrypt now confirms that the renamed entry is the one it wrote before touching its permissions, and applies them through that same confirmed handle. The decrypt still reports "Output was replaced while decrypting" as before. Windows applies no stored permissions, so nothing there needed this guard.
- **A failed decrypt of a single file no longer leaves its plaintext behind when the staging entry was moved aside.** A failed decrypt removes the partial output it staged, and for a single file it did so by name. A local process able to write to your output folder could move that file aside, leaving the name to point at something else, and the finished plaintext then stayed on disk under the name that process chose — while the same situation with a folder was cleaned up correctly. The staged file's content is now emptied through the handle it was written with before the name is removed, so it is destroyed whatever the entry is called by then.
- **A failed decrypt no longer deletes an entry someone else put at its staging name.** When a decrypt fails, FerroCrypt removes the partial output it staged next to your chosen name. It decided how to remove it — unlink a file, or delete a folder and everything in it — from what it found on disk at that moment. A local process able to write to your output folder could therefore move the staged output aside and leave a folder of its own at that name, and the failed decrypt would delete that folder and its contents. The removal now follows what the decrypt itself created: a staged file is never removed recursively, and a staged folder is removed through the handle it was created with, so it is still removed even if it was moved aside, and a substituted folder is left untouched. On Windows a staged folder is still removed by name, because nothing there can remove a whole folder tree through a handle; that removal now goes ahead only while the entry at the staging name is still the folder FerroCrypt created, so a folder substituted before that check is left untouched there too, and a staged folder that was moved aside is left where it is. A folder put at the staging name in the instant between that check and the removal is still what the removal reaches.
- **A failed key generation no longer deletes an unrelated key file.** When key generation cannot finish, it removes the `private.key` or `public.key` it had already written, and it removed that file by name. A local process able to rename or replace your output folder in the moment between the two files being written could point that name at a different folder and have FerroCrypt delete the `private.key` sitting there — a file it never wrote, in a folder that process may not have been able to change itself. The removal now stays inside the folder the key file was actually written to, and checks that the entry it removes is still the file it wrote — a key file moved aside and replaced during the failure is left in place — so it can only ever take back FerroCrypt's own file. On Windows the removal is made through the handle FerroCrypt still holds on its own key file, so an entry another process puts at that name in the same instant is never deleted.
- **A failed key generation now says when the key file it removed may still exist.** When key generation cannot finish, it removes the `private.key` or `public.key` it had already written, and it did so silently: a `private.key` given a second name by another local process in that moment survived under that name with no sign of it, and a key file replaced during the failure was left in place — correctly — without the error saying that the entry there was not FerroCrypt's. The error now reports a removed key file that still had another name, an entry left in place because it was replaced, and a removal that could not be confirmed. A key generation whose removal completed reports the same error as before.
- **Writing an encrypted file or a key file onto a drive that cannot rename in one step no longer passes through a placeholder.** Where the drive refuses an atomic no-replace rename — Apple's exFAT driver, some network shares — the finished file was committed by reserving its final name with an empty entry and renaming over it, and a local process able to write to your output folder could take over that reservation in the moment it existed. The file is now linked to its final name instead, which the operating system refuses just as atomically if the name is taken. Drives without hard links, exFAT among them, keep the reservation step and its documented window. Decrypted files already worked this way. Where that reservation step remains, a commit that fails at its final rename leaves whatever then occupies the reserved name in place and names it in the error, as a failed decrypt does (see above).
- **Encrypting or generating a key pair can no longer be left waiting forever by a substituted output folder.** Once the finished file appears under its final name, FerroCrypt asks the operating system to record that change in the folder. It reopened the folder by name to do so, so a local process able to replace your output folder in that moment could leave a named pipe at the path instead: opening a named pipe for reading waits for a writer, and the operation never returned even though the file had already been written. The path is now opened as a folder, which refuses anything else immediately.
- **The public key fingerprint shown before encryption now describes the key actually encrypted to.** The command line printed `Encrypting to: <fingerprint>` and the desktop app showed the fingerprint of the selected key, and both then read that key file again when encryption started. Replacing the file in between — by another local process, or by a folder-syncing tool pulling an update — silently changed the recipient while the fingerprint on screen stayed the same, so checking that fingerprint with the recipient proved nothing about the file produced. Both now encrypt to the key they read when they showed the fingerprint. Choosing a different key file, or switching tabs, reads the file again as before.
- **A passphrase is now cleared from memory as soon as encryption or key generation stops needing it.** Decryption already did this; the two writing paths did not. When encrypting with a passphrase, it was held until the whole operation had finished, although it is needed only while the file's key is wrapped. It is now cleared at that point, before any of your content is read, encrypted, or written — the bulk of the work, and the part whose length your input decides. The folder's structure is still examined while the passphrase is in memory, deliberately, so an unusable folder is refused before the slow key derivation runs; that pass reads names and sizes only. Key generation held the passphrase through staging, flushing, and committing both key files, although it is needed only to seal `private.key`, and now clears it as soon as that sealing returns. A large folder or a slow disk therefore no longer stretches the window in which a crash dump, swap file, or a separate memory-disclosure flaw could expose a passphrase that also opens other files.
- **A private key and its passphrase are now cleared from memory as soon as decryption stops needing them.** Both were held until the whole decrypt had finished, including extraction of the folder inside the encrypted file — whose size the sender chooses. A file built to take a long time to extract therefore widened the window in which a crash dump, swap, or a separate memory-disclosure flaw could expose credentials that open every other file encrypted to that key. The passphrase is now cleared once the key file is unlocked, and the private key itself once the matching recipient is found, both before any of the sender's content is decrypted. A passphrase used to decrypt directly is cleared at the same point.
- **File content no longer lingers in memory once it has been copied into or out of an archive.** The buffer carrying file bytes to and from the encryption layer was left as it was when a copy finished, so a fragment of the most recent file could survive in unused memory until something else overwrote it — reachable through a crash dump, a memory image, or a separate memory-disclosure flaw. It is now cleared as soon as the copy ends, matching the encryption and decryption buffers, which were already cleared.

## [0.3.0-rc.3] - 2026-07-26

### Added
- **`KdfLimit` now publishes the Argon2id bounds it is measured against:** `MEM_COST_KIB_STRUCTURAL_MAX`, `TIME_COST_STRUCTURAL_MAX`, `LANES_STRUCTURAL_MAX`, and `MEM_COST_KIB_DEFAULT`. Accepting every header the format allows previously meant copying `2 * 1024 * 1024` out of `FORMAT.md` §2.2 by hand. `HeaderReadLimits` and `KeyReadLimits` already published theirs; all three now match.
- **`KeyReadLimits` lets a caller raise the local caps applied when reading key files.** The recipient-string length cap (1,024 characters) and the `private.key` wrapped-secret cap (4,096 bytes) were fixed values sized for the X25519 key pair FerroCrypt ships, so a key with larger material could not be read at all. New `PublicKey::from_key_file_with_limits`, `PublicKey::from_recipient_string_with_limits`, and `PrivateKeyDecryptor::key_read_limits` take a `KeyReadLimits`; each builder method clamps at the structural maximum from `FORMAT.md` §7 and §8, so a caller cannot ask for more than the format can represent. The defaults are unchanged, and a file above a cap still reports `RecipientStringCapExceeded` or `PrivateKeyWrappedSecretCapExceeded`.

### Changed
- **The test-vector corpus in `ferrocrypt-lib/testvectors/suite/` is now revision 12.** Its "unknown recipient" fixtures previously used the name `mlkem768`, which `FORMAT.md` §3.3.1 reserves for a future FerroCrypt recipient type — the day such a type shipped, those fixtures would have contradicted themselves. They now use `test/unknown`, a name in the plugin namespace that FerroCrypt can never define. The manifest also records the clearer exact messages for version and capability mismatches, invalid KDF memory, and malformed FCA manifests. Implementations pinned to revision 10 or 11 should move to 12.
- **A recipient string that is not canonical lowercase Bech32 is now rejected as `InvalidFormat(FormatDefect::MalformedPublicKey)`.** Uppercase text, non-ASCII characters, a failed BIP 173 checksum, and a wrong `fcr` prefix previously reported `CryptoError::InvalidInput` with prose, so a caller could only tell a malformed public key from an unrelated input error by reading the message. All four now carry the same `malformed_public_key` diagnostic class as every other public-key rejection in `FORMAT.md` §12.1. The rejected string is no longer echoed in the message.
- **Version rejections now name the stored version domain and show the byte in hexadecimal, as required by `FORMAT.md` §12.1.** A newer outer artifact reports, for example, `Newer FerroCrypt is needed for .fcr version byte 0x02`; the private-key, public-key, and FCA archive domains follow the same pattern, while retained older-version variants say explicitly that the byte is older. The old `Newer file format (v2)` wording could be read as a FerroCrypt release number, and decimal `v255` hid that the stored field is one byte. The reserved archive version `0x00` now rejects as `MalformedArchive` per `FORMAT.md` §9.2.
- **A key file or recipient string of an unsupported key type is now rejected as the new `CryptoError::UnsupportedKeyType`: "Unsupported key type `<name>`".** Such a key — planned by `FORMAT.md` §11 for future releases or defined by an external implementation — was previously reported as "Wrong key file kind (public vs private)" or "Public key is malformed". "Wrong key file kind" now always means a real public/private mix-up; a `private.key` carrying the kind byte of another FerroCrypt file (for example a renamed `.fcr`) now reports `FormatDefect::WrongKind`, naming the raw byte.
- **`KdfParams::hash_passphrase` is no longer public.** Supported encryption, decryption, and key-generation workflows already perform Argon2id internally and enforce `KdfLimit`. Code that needs raw Argon2id output should use the `argon2` crate directly. All other `KdfParams` uses are unchanged.
- **The rejection for an existing `.incomplete` working copy now reads "Incomplete output already exists".** The old wording, "Previous .incomplete exists", was wrong when the entry was still being written by another decrypt of the same file running at the same time. Behavior is unchanged: an `.incomplete` entry the current run did not create is never reused or deleted.
- **Library error messages are now shorter, more precise, and more consistent.** Stable diagnostics use sentence case without terminal punctuation; malformed-archive and internal-error messages fit the 64-character desktop status line without losing their distinguishing text; missing inputs say "file or directory"; invalid KDF memory, archive-extension totals, and source-change diagnostics use consistent grammar and ASCII; and an archive rejected for two entries whose names differ only in capitalisation now says "duplicate entry differing only in letter case" instead of naming the comparison used. Unsupported external recipients and key types stay neutral because an upgrade may never support them, while unknown critical feature tags and newer format versions explicitly say that newer FerroCrypt is needed. Error variants and fields are unchanged.
- **On Unix systems other than Linux and macOS, decrypting a file that contains a folder now fails with "Decrypting a directory is not supported on this target".** This matches the encrypt side, which already refuses a folder there with the same kind of typed error; the rejection previously surfaced as a raw unsupported-operation I/O error. Linux, macOS, and Windows are unaffected.

### Fixed
- **On Windows, a finished encrypted file or decrypted output now has its folder entry flushed to disk, as it already did on Linux and macOS.** Nothing flushed the containing folder on Windows, so a power loss just after an operation finished could leave the output missing even though the write itself had completed. Generated key pairs already had this protection. Staged subfolders during a folder decrypt are still flushed on Linux and macOS only.
- **A host that cannot spare the Argon2id working memory now reports an error instead of terminating the process.** Key derivation asks for its working memory up front — 1 GiB at the default setting — and the previous allocation aborted immediately when the request could not be met, so a decrypt on a small or busy machine killed the program with nothing the CLI or desktop app could show. It now returns "Internal crypto error: Argon2id memory allocation failed".
- **Encrypting a folder on a filesystem that reports no inode numbers no longer fails with "Directory cycle in archive source".** Some network mounts and overlay filesystems report inode 0 for every entry, which the loop check read as the same directory seen twice — so the second subfolder was rejected and the folder could not be encrypted from that mount at all. Such directories are now skipped by that check; the entry-count, depth, and total-size limits still bound the scan. Filesystems that report real inode numbers are unaffected.
- **Two archive entries that a filesystem cannot keep apart now report "Archive path collides with an existing entry" and name the entry.** FerroCrypt's duplicate check folds ASCII case only, so a volume that also folds accented letters or Unicode normalization forms can still refuse the second entry. That refusal was safe but surfaced as a bare "file exists" I/O error with nothing to say which archive entry caused it. The root staging name keeps its own "Incomplete output already exists" message.
- **Reading a `private.key` no longer pulls in up to 16 MB before the size limit applies.** The reader takes the file's fixed header first and then reads only what that header declares, bounded by the `KeyReadLimits` wrapped-secret cap. Under the default cap an ordinary key file now costs about 82 KB instead of the format's structural maximum. The accepted files and the reported errors are unchanged.
- **A file whose kind byte says it is not what the reader expected is now reported as the wrong kind, whatever its version byte says.** Handing an `.fcr` to the private-key reader, or a `private.key` to the `.fcr` reader, previously advised you to upgrade FerroCrypt when the file also carried an unrecognised version byte. `FORMAT.md` §11.1 makes the kind byte the selector for the version byte's meaning, so the version byte says nothing until the kind matches. Both readers now report `InvalidFormat(FormatDefect::WrongKind)` first.
- **A file that carries both an unknown critical recipient and a malformed native recipient now always reports the unknown critical one.** Which of the two errors surfaced previously depended on the order the entries happened to appear in, so the same defects could be reported differently in two otherwise identical files. `FORMAT.md` §3.7 now states that each preflight step completes over the whole recipient list before the next one starts, making the reported error a function of the file's content alone.
- **A malformed recipient entry or an over-length recipient string is now reported as a malformed file, not as a resource cap you could raise.** A recipient entry whose declared body runs past the recipient region reports `InvalidFormat(FormatDefect::MalformedRecipientEntry)`, and a recipient string above the 20,000-character ceiling of `FORMAT.md` §7 reports `InvalidFormat(FormatDefect::MalformedPublicKey)`. Both previously reported `RecipientBodyCapExceeded` or `RecipientStringCapExceeded`, which told you to raise a limit that could never accept the input. A body or string that is genuinely present and merely above your configured cap still reports the cap error.
- **An encrypted file that declares a header too small to hold the fixed header section is now rejected in the order required by `FORMAT.md` §3.7.** The reader first reads the declared header and the header MAC: a file that ends before they are complete reports `InvalidFormat(FormatDefect::Truncated)`, and only a fully framed undersized header reports `InvalidFormat(FormatDefect::MalformedHeader)`. Previously every undersized declaration reported the malformed-header error, even when the file was simply cut short.
- **A non-canonical encoding of an X25519 public key is now rejected everywhere a public key is read, as required by `FORMAT.md` §2.4.** X25519 treats several byte patterns as the same key, but FerroCrypt binds the exact bytes into fingerprints, recipient strings, and the wrapping step. A non-canonical encoding (for example one recovered from another tool with the top bit set) previously produced an encrypted file that the matching private key could not open, and gave one key a second fingerprint. `PublicKey::from_x25519_bytes`, `PublicKey::from_recipient_string`, `public.key` files, and `decode_x25519_recipient_string` now reject such values as `InvalidFormat(FormatDefect::MalformedPublicKey)`. Keys generated by FerroCrypt are always canonical and are unaffected.
- **A recipient entry with a wrong body length is now rejected before any key derivation runs, as required by `FORMAT.md` §3.7.** Such a file previously ran the full private-key unlock (a deliberately slow Argon2id step) before the cheap length check rejected it. `Decryptor::open` and `probe_recipient_mode` now report `InvalidFormat(FormatDefect::MalformedRecipientEntry)` directly; the final error for a full decrypt attempt is unchanged.
- **Decryption now rejects an authenticated empty final payload chunk after non-empty data, as required by `FORMAT.md` §5.** FerroCrypt writers have never produced this non-canonical encoding. A file using it now returns `InvalidFormat(FormatDefect::MalformedPayloadStream)` instead of decrypting successfully.
- **Authenticated files with incomplete internal archive headers, extension regions, or manifests now return `MalformedArchive` with the affected region.** These structural defects previously appeared as generic I/O errors. Filesystem failures and truncated or modified encrypted payloads keep their existing error types.
- **Decryption no longer waits indefinitely if a completed output file is replaced with a named pipe before its permissions are applied.** The final permission update now opens without blocking and accepts only a regular file.
- **Public-key decryption now uses the same opened encrypted file for validation and decryption.** Replacing the path while the private key is being unlocked no longer changes which file is decrypted. Passphrase decryption already had this behavior.
- **Encrypting a directory to a destination inside that directory no longer includes FerroCrypt's staging file in the archive.** Source entries are recorded before output staging begins, so the restored tree does not contain FerroCrypt's own output. Archive-limit failures also occur before passphrase derivation begins.
- **Key generation now commits `private.key` before `public.key` and flushes the key directory after each commit.** Process interruption cannot leave a usable `public.key` without its matching `private.key`. On filesystems that support directory flushing, the same guarantee covers power loss. Other filesystems depend on their own ordering guarantees after power loss. A genuine flush failure stops key generation with an error.
- **Error messages containing untrusted names now apply their length limit after escaping.** Escaped file names, archive paths, and recipient strings can no longer exceed the intended display width.
- **"Already exists" conflict messages now escape control and text-direction characters across the whole path, not only in the final name.** Such a character in an intermediate directory name was previously shown unescaped, so the message could carry a terminal escape sequence or a visually reordered name into a terminal or log. The directory portion is still shown in full and untruncated so the conflict stays easy to locate.

- **The payload chunk-count limit now reports "Encrypted file exceeds supported data size" when it trips during encryption.** Previously that limit — reachable only for payloads near 256 TiB under raised archive limits — surfaced as a plain I/O error on the encrypt side, while the same condition on the decrypt side already produced the typed error.

- **Archive path components are now capped at 244 bytes.** A file or directory name longer than that could previously be encrypted but not decrypted: extraction stages output under a working name 11 bytes longer than the original, and the common filesystems (ext4, XFS, APFS, NTFS) limit names to 255 bytes. - **A source tree whose archive manifest would exceed `max_manifest_bytes` is now rejected while the tree is being scanned**, instead of after the whole scan finished, so the rejection is faster and writer memory stays bounded near the cap.
- **Decrypted files are now synced to stable storage before the output is given its final name.** A power loss right after a decrypt finished could previously leave incompletely written file content under the final output name, with nothing left to signal that the output was partial. Each extracted file is now flushed to disk before the rename, matching the durability the encrypt side already provides for its output.
- **Decrypting a folder now also syncs the folder's directory structure before the output is given its final name, not just the file contents.** On Linux and macOS, only the extracted files had been flushed; the directory entries linking them had not. A power loss right after a folder decrypt finished could therefore leave the output present under its final name while nested files were missing or empty on filesystems where flushing a file does not also make its containing directory entry durable. Each staged subdirectory and the staged root folder are now flushed before the rename.
- **Archive rejections are now typed errors instead of message strings.** A hostile or corrupt archive inside a `.fcr` previously surfaced as `CryptoError::InvalidInput` with prose, distinguishable only by reading the message. Structural defects now surface as `MalformedArchive`, `UnsafeArchivePath`, or `InvalidArchiveTree` (each naming the violated rule), and every archive resource cap has its own variant carrying the offending value and the configured cap (`ArchiveEntryCountCapExceeded`, `ArchivePathDepthCapExceeded`, and the rest of the `Archive*CapExceeded` family). Callers that matched on `InvalidInput` for these cases should match the new variants; message text has changed accordingly.
- **A `private.key` whose wrapped secret exceeds the local cap is now reported as `PrivateKeyWrappedSecretCapExceeded`** instead of "Private key is malformed". The file may be structurally valid for a future key type; the reader's resource policy is the actual constraint.
- **`Decryptor::open` on a path inside an unreadable directory now reports the permission error** instead of "Input file or folder missing", so a permissions problem is no longer mistaken for a missing file.
- **Decryption and authentication failures now use consistent, plain wording.** Messages that previously exposed internal terms — the recipient type name, "unwrap failed", "MAC mismatch" — or asserted tampering now name the likely cause in user terms and keep the credential-or-modification ambiguity (a failed authentication cannot tell a wrong credential from a modified or corrupted file). The `CryptoError` variants and their fields, including `type_name`, are unchanged, so code matching on the error is unaffected; only the rendered text changed.
    - Passphrase file, wrong passphrase → `Decryption failed: wrong passphrase or modified file`.
    - `private.key` unlock → `Private key unlock failed: wrong passphrase or modified key file`.
    - Header authentication (passphrase and public-key) → `Decryption failed: file header was modified or corrupted`.
    - Payload authentication → `Decryption failed: file data was modified or corrupted`.
- **A public-key decrypt with a private key that opens none of the file's supported recipients now reports `RecipientUnwrapFailed` ("Decryption failed: no matching recipient or modified file"), not `NoSupportedRecipient`.** `FORMAT.md` §12 treats a wrong key and a file with no supported recipient as separate cases; the wrong-key-or-modified-recipient case belongs with the other unwrap failures. `NoSupportedRecipient` is now used only for a file whose recipient type this build cannot read, and reads "Decryption failed: no supported recipient". Code that matched `NoSupportedRecipient` for the wrong-key case should match `RecipientUnwrapFailed` instead.
- **Resource-limit error messages now say "limit" instead of "cap" and read in plain terms.** The `*CapExceeded` family and the related KDF, header, recipient, and archive limit errors previously used internal wording ("KDF resource cap exceeded", "Recipient body cap exceeded", "wrapped-secret", "chunk-count cap"). They now read as plain limits — for example "Passphrase memory over limit (1048576 KiB, limit 524288)", "Too many recipients (100 entries, limit 64)", and "Archive is too large (limit 99 bytes)" — keeping the offending value where it fits and showing only the configured limit for the large 64-bit byte totals that would otherwise not fit the line. `UnknownCriticalRecipient` now reads "Unsupported recipient `<type>`. Upgrade FerroCrypt." and `PayloadChunkCountExceeded` "Encrypted file exceeds supported data size". The `CryptoError` variants and their fields are unchanged, so code matching on the error is unaffected; only the rendered text changed.
- **Internal "should not happen" errors now use a consistent prefix.** `CryptoError::InternalInvariant` and `CryptoError::InternalCryptoFailure` previously displayed their raw marker (some markers already embedded "Internal error:", some did not). They now render "Internal error: {marker}" and "Internal crypto error: {marker}", with the marker bounded so the message stays within the status-line width; the full marker remains in the variant payload for bug reports. These errors indicate a library bug and are not expected in normal use.
- **The desktop status line no longer overflows on a long error.** A long OS error string or archive path could previously run past the one-line status width. The desktop now elides an over-long error to fit — keeping the leading text and eliding the path — while the library and CLI still return the full message. This is a desktop UI change only; no library behavior changed.

### Fixed
- **The CLI no longer crashes when the program reading its output closes the pipe early.** Piping the CLI into a reader that exits first — for example `ferrocrypt fingerprint key.pub | head` — could previously end in a panic with exit code 101 instead of stopping cleanly. A closed output pipe is now treated as a normal end of output.
- **The CLI now exits with a non-zero status when its interactive line editor cannot start.** It previously printed the error but exited as success, so a script could not detect the failure.

### Security
- **Passphrase and key-pair encryption now reject Argon2id parameters below a memory floor.** `Encryptor::kdf_params` and `KeyPairGenerator::kdf_params` previously accepted any structurally valid memory cost — including values far too low to protect a passphrase — so a caller could accidentally produce a `.fcr` or `private.key` with weak key-stretching. A memory cost below 19 MiB (the OWASP Argon2id minimum) is now rejected at write time with the new `CryptoError::KdfBelowWriteFloor`. The floor is hard, with no override. Decryption is unchanged: a file written before the floor existed still decrypts.
- **The final rename that commits a decrypt now uses the same directory handle as extraction (Linux and macOS).** Promoting the staged `.incomplete` to its final name previously re-resolved the output directory by path, so a directory swapped in on the way to it during the run could redirect the commit — leaving the real plaintext staged in the original directory while an attacker-planted `.incomplete` in the swapped-in directory was promoted under the final name instead. The rename is now anchored to the directory handle opened at the start of extraction, matching the failure-path cleanup and the final permissions step. On Windows the commit stays path-based — single-file decrypts keep the kernel atomic no-replace move, directory decrypts the documented best-effort rename — because a handle-relative no-replace rename there needs an `unsafe` Win32 call the crate forbids; see `SECURITY.md`.
- **The final permissions step of a decrypt now uses the same directory handle as extraction.** Applying the root entry's permissions after the rename previously re-opened the output directory by path, so swapping a directory on the way to it during the run could redirect that final permissions change to a same-named entry elsewhere. The handle opened at the start of extraction is now reused, the same protection the failure-path cleanup already had.
- **The "Output already exists" error can no longer carry raw attacker-chosen characters.** The pre-extraction occupancy check embedded the archive's root name in its message without escaping, so a hostile archive could place invisible or direction-changing characters there. The name is now escaped like every other archive-derived text in error messages.
- **The file or folder being encrypted can no longer be swapped mid-run through a re-resolved path.** Encrypting a single file now reads its size, permissions, and content from one handle opened at the start, so replacing the file — or any folder on the way to it — while encryption runs cannot substitute different content. When encrypting a folder, a Windows junction swapped in at the input path between the pre-check and the open is now rejected instead of silently followed; the equivalent identity check already existed on Unix.
- **Error messages can no longer carry attacker-chosen control characters or look-alike Unicode.** Text an attacker may have picked — archive entry paths, source-tree file names, and the echoed input of a rejected recipient string — is now escaped and truncated before it is embedded in an error message, so terminal-bound errors cannot smuggle escape sequences or visually reordered names.
- **A FIFO swapped in for a source file can no longer stall encryption.** Encryption reads each source file twice (a scan pass and a content pass); replacing a scanned file with a FIFO before the content pass previously blocked the process indefinitely inside the open call on Unix. The content-pass open is now non-blocking and the substituted entry is rejected, matching the guard that decryption, probing, and key-file reading already apply.
- **HMAC and HKDF working state is now wiped from memory when dropped.** The internal hash state these computations derive from per-file keys was previously freed without wiping after each header authentication or key derivation, the same memory-residue class as the Argon2id fix in 0.3.0-beta.3. That state is now zeroized when each computation is dropped.

## [0.3.0-beta.3] - 2026-06-11

### Added
- **`KDF_PARAMS_SIZE` is now re-exported** so callers working with `KdfParams::to_bytes` / `KdfParams::from_bytes` can name the 12-byte serialized length instead of hard-coding it.

### Changed
- **`HeaderTampered` now reads "Decryption failed: header tampered or corrupted after unlock".** The previous wording asserted tampering, but a failed header MAC cannot distinguish deliberate modification from storage corruption. The payload and truncation errors already say "or corrupted"; this message now matches them.
- **`KdfParams::hash_passphrase` now takes its salt as `&[u8; ARGON2_SALT_SIZE]`** (the constant is re-exported as `ferrocrypt::ARGON2_SALT_SIZE`). A wrong-sized salt was previously misreported at runtime as an internal Argon2id failure; it is now a compile error. Callers already passing a 32-byte array are unaffected; callers holding a slice must convert with `try_into()`.

### Fixed
- **Encrypting a directory with many subdirectories in one folder no longer fails with "Too many open files".** The metadata pass held one open directory handle per discovered subdirectory, so a folder with more subdirectories than the process file-descriptor limit (commonly 256 on macOS) could not be encrypted. Open handles now track the depth of the tree instead of its width.
- **A transient interrupted read (EINTR) no longer aborts encryption or decryption.** A signal delivered while a long stream was being read could previously abort a multi-gigabyte operation with an I/O error — or, on decrypt, surface a false "tampered or corrupted" payload error — depending on where the interruption landed. Interrupted reads are now retried in every streaming path.
- **`validate_private_key_file` now rejects a `private.key` whose wrapped-secret length is not 48 bytes.** Such a file can never unlock (`FORMAT.md` §8 fixes the wrapped X25519 secret at a 32-byte scalar plus the 16-byte tag), but the validator previously reported it as well-formed.
- **Progress events no longer fire for a passphrase that exceeds the 4096-byte cap.** `DerivingPassphraseWrapKey` and `UnlockingPrivateKey` are now emitted only after the passphrase-length check passes, so a progress-driven UI no longer shows a key-derivation phase for an operation that is rejected without any KDF work.
- **A decrypt whose output is already in place no longer reports failure when the final permissions step fails.** Applying the root entry's mode after the rename is now best-effort: the decrypt succeeds and the output keeps the stricter staging permissions (`0o600` for a file, `0o700` for a directory). Previously such a decrypt returned an error while the complete plaintext stayed on disk at the final name, where the automatic `.incomplete` cleanup could no longer reach it.

### Security
- **Argon2id working memory is now zeroized after key derivation.** The block buffer Argon2id works in (up to the configured memory cost, 1 GiB at the default settings) was previously freed without wiping after every passphrase operation, leaving material in process memory from which the derived wrap key could be recomputed by anything able to read freed memory (swap, core dumps, a memory-disclosure bug). The buffer is now wiped when derivation completes, on error paths included.
- **Non-canonical Bech32 recipient strings are now rejected.** `FORMAT.md` §7 requires decoders to reject non-canonical 5-to-8 padding; previously a second, distinct `fcr1…` string with non-zero padding bits decoded to the same accepted key. The decoded key bytes and fingerprint were identical, so no key confusion was possible — but tools treating the recipient string itself as a canonical identifier could be misled, and a non-canonical `public.key` was silently accepted where the spec requires rejection.
- **Decryption, probing, and key-file reading now refuse FIFOs, sockets, and device nodes.** Pointing `Decryptor::open`, any `decrypt`, `probe_recipient_mode`, or a key-file path at a FIFO (for example an attacker-placed pipe named `something.fcr`) previously blocked the process indefinitely inside the open call. These inputs now fail fast with `CryptoError::InvalidInput`, matching the rejection the encrypt side has always applied, and the open itself can no longer block.
- **Closed a race on the encrypt-side input-directory open (Unix).** A symlink or replacement directory swapped in at the input root between FerroCrypt's pre-check and its open could previously be archived in place of the directory the user selected. The opened directory's identity is now verified against the pre-check, and any swap is rejected with "Input directory changed during archive".

## [0.3.0-beta.2] - 2026-05-24

### Fixed
- **`KeyPairGenerator` now honors a `kdf_limit` raised above the 1 GiB default.** Generating a key pair with `kdf_params.mem_cost` above 1 GiB together with a matching `KeyPairGenerator::kdf_limit` was wrongly rejected with `KdfResourceCapExceeded`; the private-key writer no longer re-imposes the default memory ceiling.
- **`.fcr` files missing the 32-byte header MAC tag are now always reported as truncated.** A file that was both structurally malformed and missing its MAC tag could previously surface `InvalidFormat(MalformedHeader)` ("File header is malformed") instead of `InvalidFormat(Truncated)` ("File is truncated or corrupted"). The header parser now reads the MAC tag immediately after the header region, before any structural parse — matching the decryption order in `FORMAT.md` §3.7.
- **Public-key decryption with an unrelated private key now returns `CryptoError::NoSupportedRecipient`** instead of `RecipientUnwrapFailed { type_name: "x25519" }`. Callers that pattern-match on the old per-candidate variant for the wrong-key case should switch to `NoSupportedRecipient`. The passphrase wrong-passphrase case still returns `RecipientUnwrapFailed { type_name: "argon2id" }`.

### Security
- **Windows: single-file decrypts now finalize with an atomic no-clobber move.** When you decrypt a `.fcr` that contains one file, the final step of renaming the staged `.incomplete` to the chosen output name is now a single kernel call that refuses to overwrite if the name is already taken. Previously a local process that created the final name in the brief window between FerroCrypt's pre-check and rename could have its file silently overwritten by ours. Decrypts of directory archives on Windows still use the older check-then-rename sequence; see `SECURITY.md` for the remaining limitation.
- **Encryption refuses to write a stream that would exceed the `FORMAT.md` §5 chunk-counter cap.** The writer could previously emit a spec-invalid chunk before rejecting on the next operation; the matching reader gains the same early rejection. Default `ArchiveLimits` cap plaintext at 64 GiB, so this only matters for callers who raise the cap toward the spec ceiling (~281 TB).
- **`private.key` files with malformed or unknown-critical extension TLVs are refused on both write and read.** v1 key generation emits empty extension bytes and is unaffected; this only matters for hand-crafted or future-version key files.
- **`PrivateKeyDecryptor::decrypt` re-checks the input file before unlocking `private.key`.** A file replacement between `Decryptor::open` and `.decrypt` no longer triggers the Argon2id `private.key` unlock or its `UnlockingPrivateKey` progress event for a file the decrypt path would refuse anyway.
- **`DeleteOnError` cleanup follows the output directory chosen at the start of decryption.** A local process that renamed the destination between a failed decrypt and the automatic `.incomplete` cleanup could previously redirect the cleanup to a different directory; that race is now closed.

## [0.3.0-beta.1] - 2026-05-11

### Added
- **FCA archive forward-compatibility hooks.** The FCA payload format now reserves an archive-level extension region (`archive_ext`) and per-entry extension regions (`entry_ext`) for future opt-in metadata (timestamps, xattrs, ACLs, symlinks, hardlinks, sparse files). v1 writers emit zero-length regions; v1 readers reject any unknown critical TLV (`0x8001..=0xFFFF`) and skip any unknown ignorable TLV (`0x0001..=0x7FFF`) under the same canonicality rules already used for `.fcr` header `ext_bytes`. The wire-format change is one-time: FCA fixed header grows from 23 to 27 bytes (adds `archive_ext_len: u32`); each manifest entry's fixed prefix grows from 14 to 18 bytes (adds `entry_ext_len: u32`). New `ArchiveLimits` caps — `max_archive_ext_bytes` (default 64 KiB), `max_entry_ext_bytes` (default 64 KiB), `max_total_entry_ext_bytes` (default 64 MiB), `max_tlv_value_bytes` (default 16 MiB) — bound extension allocations before any output. See `FORMAT.md` §9.

### Security
- **Hardened extraction unified across Linux, macOS, and Windows.** Previously, hardened extraction ran only on Linux and macOS; Windows fell back to a path-based extractor with documented symlink-race exposure. A symlink at any component of an extraction path is now rejected on every supported OS. On Windows, directory opens additionally fail closed on any NTFS reparse point — including junctions and mount points. File creation refuses to follow symlinks. Permissions are always set on an open handle, never via a re-resolved path. The previous Windows path-based fallback is removed.
- **Closed two narrow Unix permission-window leaks during archive extraction.** (1) A single-file root with a permissive manifest mode (e.g. `0o644`) was briefly readable by other local users between the `chmod` after content streaming and the final no-clobber rename; the staged file now stays at `0o600` throughout extraction and is chmod'd to the manifest mode AFTER promotion, so plaintext is never visible at a wider mode under either the `.incomplete` name or the final name. (2) A staged `.incomplete` directory was created with `mkdir(0o777) & ~umask`, briefly leaving it world-traversable under a permissive process umask before a follow-up `chmod(0o700)`; the staged directory is now created with `0o700` atomically via cap-std's `DirBuilderExt::mode`. Windows is unaffected (no Unix mode semantics).
- **Documented a small Windows race window during final rename.** When decryption finishes on Linux or macOS, the rename of the `.incomplete` file to its final name atomically refuses to overwrite. On Windows it is "check, then rename" with a brief gap between the two — a process that creates the final name in that gap has its file silently overwritten by ours. The decrypted file still goes where you asked (Windows renames don't follow symbolic links), so the failure mode is integrity, not confidentiality. Matters only when an untrusted local process can write to your output folder. No code change; the behaviour has always been this way and is now explicitly documented. See `SECURITY.md`.

### Added
- **`Encryptor::kdf_params(KdfParams)` and `KeyPairGenerator` builder.** The encrypt-side passphrase path and the new key-pair generator both accept an explicit `KdfParams` override, replacing the previous all-or-nothing reliance on `KdfParams::default()`. The free function `generate_key_pair(...)` is preserved as a thin wrapper around `KeyPairGenerator::with_passphrase(...).write(...)` for backwards compatibility. `KdfParams` is now publicly re-exported from `ferrocrypt`.
- **New `Encryptor` / `Decryptor` value-type API.** Pick the recipient kind at construction (`Encryptor::with_passphrase(pass)` / `with_public_key(public_key)` / `with_public_keys(iter)`); optional `.save_as(path)` / `.archive_limits(limits)` / `.kdf_limit(limit)` / `.header_read_limits(limits)` / `.kdf_params(params)` builders; finalize with `.write(input, output_dir, on_event)`. `Decryptor::open(input)` probes the file's recipient list with no crypto and returns a typed `Decryptor::Passphrase` or `Decryptor::PrivateKey` variant, so passing the wrong credential is a compile error rather than a runtime failure. Multi-recipient encrypt is supported: `with_public_keys([alice, bob])` produces a single `.fcr` either recipient can decrypt with their own private key. New `PublicKey` and `PrivateKey` types replace raw byte arrays in the public API.
- **Bech32 recipient strings (`fcr1...`)** for human-readable public-key exchange. Build a `PublicKey` via `PublicKey::from_recipient_string("fcr1…")` and render with `to_recipient_string()`. Copy-paste corruption is detected at decode. CLI: `encrypt --recipient` / `-r` takes an `fcr1…` string directly (repeatable, mixable with `--public-key` / `-k`); the `public.key` file is itself a single-line UTF-8 recipient string, so `cat public.key` is enough.
- **SHA3-256 public-key fingerprints** for out-of-band verification, domain-separated by recipient type so future native types (post-quantum, hybrid KEMs) cannot collide with X25519 fingerprints. CLI: new `fingerprint` subcommand (alias `fp`); `keygen` and `encrypt` print the relevant fingerprint. Desktop app shows the fingerprint with a copy-to-clipboard button.
- **`ArchiveLimits` and archive resource caps**, applied symmetrically on encrypt and decrypt. Defaults: at most 250,000 entries, 64 GiB total file content, 64 path segments. Decrypt caps fire before any allocation to bound DoS exposure; the encrypt-side preflight refuses trees the default-config decrypt would refuse, preventing the "encrypt fine but cannot decrypt your own file" footgun. Override via `Encryptor::archive_limits(limits)` and the decryptor variants. A `.fcr` written under elevated caps must be decrypted under matching caps.
- **`HeaderReadLimits` exposed publicly** so callers can opt into elevated header / recipient-count / recipient-body caps when files legitimately exceed the conservative defaults. New `Decryptor::open_with_limits` and `probe_recipient_mode_with_limits` propagate the limits; either decryptor variant also exposes `.header_read_limits(limits)`.
- **`--max-kdf-memory <MiB>` flag on `decrypt`** to cap accepted KDF memory cost. Library: attach a `KdfLimit` via `.kdf_limit(limit)`; out-of-budget files fail with `KdfResourceCapExceeded`. Default ceiling 1 GiB.
- **`--keep-partial` flag on `decrypt`** for backup-recovery and forensic flows: keep the staged `.incomplete` plaintext when a decrypt fails mid-stream so the caller can inspect or recover authenticated chunks already written. Library: opt in via `.incomplete_output_policy(IncompleteOutputPolicy::RetainOnError)` on either decryptor variant. Without the flag the default is `DeleteOnError` — see "Default cleanup-on-error" under **Changed**.
- **`--save-as` / `-s` flag on `encrypt`** to choose the encrypted output filename. `--output-dir` is optional when `--save-as` is given.
- **`--allow-double-encrypt` flag on `encrypt`.** Inputs whose first 4 bytes match the FerroCrypt magic warn and refuse by default; an interactive shell prompts y/N (default N), a non-interactive shell exits 1.
- **Early conflict detection** for `encrypt` and `keygen` — fails before overwriting an existing `.fcr` file or key pair.
- **Subcommand help, descriptions, and aliases.** `enc` for `encrypt`, `dec` for `decrypt`, `gen` for `keygen`, `fp` for `fingerprint`.
- **Slint-based desktop app** (`ferrocrypt-desktop`) with **Password** and **Key pair** tabs. Inline key generation in the Key pair tab; auto-transition to Key pair Encrypt with the public key pre-filled. "Save As" dialog, magic-byte mode detection, conflict warnings, key file validation on selection, password strength indicator (scoring adapted from Proton Pass).
- **Independent version domains for `.fcr`, `private.key`, and `public.key`.** Three independent version domains, each exposed via public constants — `FCR_FILE_VERSION` for the `.fcr` outer file; `PRIVATE_KEY_VERSION` (current writer) and `PRIVATE_KEY_V1_VERSION` (pinned v1) for `private.key`; `PUBLIC_KEY_VERSION` (current writer) and `PUBLIC_KEY_V1_VERSION` (pinned v1) for `public.key`. The three domains replace the former shared `VERSION` byte: a bump to the outer `.fcr` file format does not bump key-pair compatibility, and a key-pair compatibility bump does not require an outer file bump. The encrypt/decrypt symmetry rule (`FORMAT.md` §11) — "a release MUST NOT accept a public key for encryption unless the same key-pair generation remains supported for private-key decryption" — is structurally enforced across both key parsers. New `CryptoError::UnsupportedVersion` variants `OlderPublicKey { version }` and `NewerPublicKey { version }` carry the rejected public-key version separately from the existing `OlderKey` / `NewerKey` variants used for `private.key` rejection.
- **`MixingPolicy::Custom { compatibility_class }`** variant on `CryptoError::IncompatibleRecipients`, reserved for future native compatibility classes (starting with the upcoming post-quantum `x25519-mlkem768` recipient). The two existing variants (`Exclusive`, `PublicKeyMixable`) keep their shape.
- Progress messages (`Deriving passphrase key…`, `Unlocking private key…`, `Encrypting…`, etc.) printed to stderr.

### Changed
- **Breaking: native FerroCrypt Archive (FCA) format replaces the restricted POSIX ustar archive payload.** The inner archive layer that carries directory contents inside the encrypted payload is now a small native format with a manifest-first design (full path-grammar, tree-shape, and duplicate validation completes before any file is written to disk). Pre-`0.3.0` `.fcr` files (which used the legacy `.fcs` / `.fch` extensions and an internal zip payload) become unreadable. User-visible consequences:
    - **Stricter portable path subset.** Archive paths containing Windows-reserved characters (`< > : " | ? *`), Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `CLOCK$`, `COM1..9`, `LPT1..9`) — including in extension stems (e.g. `CON.txt`), ASCII control bytes (`0x00..=0x1F`), trailing `.`, or trailing space are now rejected at encrypt and decrypt. The same rules apply on every supported OS, not just Windows.
    - **ASCII-case-insensitive duplicate paths rejected.** A single archive cannot contain both `Foo.txt` and `FOO.TXT` even though the FerroCrypt grammar itself is case-sensitive — the rejection prevents a case-insensitive-filesystem collision at extraction time on macOS HFS+ / Windows NTFS.
    - **Per-file 8 GiB ceiling removed.** The previous `ustar`-imposed cap (8,589,934,591 bytes per file, one byte short of 8 GiB) is gone; FCA uses a `u64` size field. Cumulative-bytes cap from `ArchiveLimits::max_total_plaintext_bytes` (default 64 GiB) still applies.
    - **No archive-format extension records.** PAX / GNU / Solaris extension records were a hardening burden in the ustar subset; they are not representable at all in FCA.

  See `ferrocrypt-lib/FORMAT.md` §9 for the byte-level FCA spec and `ferrocrypt-lib/FORMAT.md` design-rationale section for why a custom format was preferred over a tar subset.

- **Breaking:** New on-disk format family (the v1 byte-level layout defined in `ferrocrypt-lib/FORMAT.md`) replaces the pre-`0.3.0` zip-based artefacts. Single `.fcr` extension replaces `.fcs` / `.fch`. The new `.fcr` is a single container with a typed **recipient list**, not a per-mode envelope: the symmetric-vs-hybrid distinction is derived from the list, not encoded in the header. Two native recipient types are defined: `argon2id` (passphrase, exclusive — must appear alone) and `x25519` (public-key, mixable — multiple slots in one file are supported and the decrypt loop iterates). Mixed lists (e.g. `argon2id` plus `x25519`) reject before any KDF runs. The `.fcr` outer file, `public.key`, and `private.key` are independently versioned and all currently sit at byte `0x01`; future bumps in any one domain do not force the others to bump.
- **Breaking:** Hybrid encryption migrated from RSA-4096 (OpenSSL) to **X25519 ECDH + HKDF-SHA3-256 + XChaCha20-Poly1305** envelope encryption. Removes the OpenSSL C dependency — the project is now pure Rust. All-zero shared secrets are rejected as a small-order key defence. Pre-`0.3.0` hybrid files cannot be decrypted; old key pairs must be regenerated.
- **Breaking:** Both modes use a per-file random **32-byte `file_key`** indirection (age-inspired). The recipient body seals the random `file_key`; the payload AEAD key and the header MAC key are derived separately from `file_key`, so a compromise of one subkey does not reveal the other. Argon2id parameters: 1 GiB memory, time cost 4, parallelism 4. Payload is XChaCha20-Poly1305 STREAM-BE32 over 64 KiB chunks. The header MAC is verified after a recipient successfully unwraps a candidate `file_key`; MAC verification is the final acceptance gate. Multi-recipient MAC failures surface as `HeaderMacFailedAfterUnwrap { type_name }` and the loop continues; single-recipient MAC failures surface as `HeaderTampered`.
- **Breaking:** `public.key` is a **UTF-8 text file** containing the canonical Bech32 `fcr1…` recipient string optionally followed by a single trailing LF (no other surrounding whitespace).
- **Breaking:** `private.key` v1 is passphrase-protected via **Argon2id + HKDF-SHA3-256 + XChaCha20-Poly1305** with permissions `0o600` on POSIX. The cleartext header is bound to authentication, so tampering any field fails the unlock. Wrong passphrase and tampered file are indistinguishable at the AEAD layer; both surface as `KeyFileUnlockFailed` with wording `"Private key unlock failed: wrong passphrase or tampered file"`. The public/private halves are cross-checked at unlock; mismatch surfaces as `MalformedPrivateKey`, catching structurally valid files whose halves were sealed inconsistently.
- **Breaking:** Forward-compatible authenticated **TLV extension region** is present in both `.fcr` and `private.key` (empty in v1.0). Reserved-tag and critical-tag rules let future format additions reject older readers safely. Cap: 64 KiB.
- **Breaking:** SHA-3 unified across the spec — HMAC-SHA3-256 for the header MAC, HKDF-SHA3-256 for every key derivation, SHA3-256 for fingerprints and the internal Bech32 checksum.
- **Breaking (CLI):** Operation-oriented subcommand surface. `symmetric` / `sym` and `hybrid` / `hyb` are removed; everything goes through `encrypt` (alias `enc`) and `decrypt` (alias `dec`). `keygen` (alias `gen`) and `fingerprint` (alias `fp`) keep their names. Mode is decided by what the user supplies: `encrypt` runs in passphrase mode by default and switches to public-key mode when `--recipient` / `-r` or `--public-key` / `-k` is given; `decrypt` reads the file's recipient list and routes itself. The `recipient` / `rc` subcommand is removed because `public.key` is itself a single-line `fcr1...` text file. Long-flag renames: `--input-path` → `--input`, `--output-path` → `--output-dir`, `--key` → `--public-key` (encrypt) / `--private-key` (decrypt). Short-flag case split: `-k` is the shareable public key, `-K` is the secret private key. Removed flags: `--bit-size` / `-b`, `--large` / `-l` (RSA-only).
- **Breaking (CLI):** Passphrases are no longer accepted as CLI argument values. They are prompted interactively with hidden input and confirmation on encrypt and keygen. For non-interactive use (scripts, CI) set the `FERROCRYPT_PASSPHRASE` environment variable. Empty passphrases are rejected.
- **Breaking (library API):** `PublicKey::from_bytes` now returns `Result<PublicKey, CryptoError>` and structurally rejects the all-zero X25519 public key at construction. The same reject runs at every ingress that loads a public key. Callers that previously chained `PublicKey::from_bytes(b).validate()?` should now write `PublicKey::from_bytes(b)?.validate()?`.
- **Breaking (library API): pre-auth vs authenticated recipient mode are now distinct types.** `EncryptionMode` is renamed to `UnauthenticatedRecipientMode` and its `Recipient` variant is renamed to `PublicKey` (so the variants are now `Passphrase` / `PublicKey`); the pre-1.0 `EncryptionMode::Symmetric` / `Hybrid` legacy names from earlier in this release line are gone. The cheap probe function `detect_encryption_mode` / `_with_limits` is renamed to `probe_recipient_mode` / `_with_limits`. A new `AuthenticatedRecipientMode` (with public discriminant `AuthenticatedRecipientModeKind`) is sealed inside the crate — only the decrypt path can construct it — and is surfaced on `DecryptOutcome::recipient_mode`. The two-type split moves the "structural classification, not a security claim" warning out of a docstring and into the type system: a value that travels through `probe_recipient_mode` cannot be passed where `AuthenticatedRecipientMode` is expected, and an `AuthenticatedRecipientMode` value cannot be forged from probe output. Display strings: `Passphrase` is unchanged; the `PublicKey` variant renders as `"public-key"` (was `"recipient"` for the old `Recipient` variant), so the `DecryptorModeMismatch` message reads e.g. "Decryptor expects passphrase file, got public-key". Desktop tab names are unchanged.
- **Breaking (library API):** Folded `CryptoError::PassphraseRecipientMixed` and the previous `CryptoError::IncompatibleRecipients { policy }` into `CryptoError::IncompatibleRecipients { type_name: String, policy: MixingPolicy }`. Encrypt-side and decrypt-side mixing rejections both surface the same variant. Existing `match err { CryptoError::PassphraseRecipientMixed => ... }` arms must be rewritten; arms that destructured `policy` only must add a `type_name` binding (or `..`).
- **Breaking (library API): writer caps mirror reader defaults.** A default-configured `Encryptor` now rejects configurations that would produce a `.fcr` file a default-configured `Decryptor::open` refuses, instead of silently producing them. Specifically: `Encryptor::with_public_keys(...)` followed by `.write(...)` rejects `recipients.len() > 64` (the default `HeaderReadLimits::RECIPIENT_COUNT_DEFAULT`) with `RecipientCountCapExceeded` before any X25519 ECDH runs; `Encryptor::with_passphrase(...).kdf_params(P)` rejects `P.mem_cost > 1 GiB` (the default `KdfLimit`) with `KdfResourceCapExceeded` before Argon2id runs. The writer-side preflight also checks the per-entry `body_len` and the exact `header_len` it will emit against the same `HeaderReadLimits`, so all three header axes — recipient count, body length, header length — refuse to produce above-cap output unless the caller raises that axis explicitly. To produce a file with more recipients or any other axis above default, the caller MUST opt in via the new `Encryptor::header_read_limits(HeaderReadLimits)` and `Encryptor::kdf_limit(KdfLimit)` builders, AND the receiving decryptor MUST be configured with matching limits (`Decryptor::open_with_limits` and `*::kdf_limit`). `KeyPairGenerator::kdf_params` follows the same rule for the passphrase that seals `private.key`; the new `KeyPairGenerator::kdf_limit` is the matching opt-in. Pre-existing files are unaffected — only the encrypt/keygen surfaces tighten.
- **Breaking (library API): writer-side structural KDF validation.** `Encryptor::with_passphrase(...).kdf_params(P)` and `KeyPairGenerator::kdf_params(P)` now reject structurally invalid Argon2id parameters (`lanes` outside `1..=8`, `time_cost` outside `1..=12`, `mem_cost` outside `[8 × lanes, 2 GiB]`) with `CryptoError::InvalidKdfParams(...)` at `write` time, applying the same structural rules the reader applies. Previously these would have flowed through to argon2's runtime check and produced an artefact no FerroCrypt reader could open.
- **Breaking (library API):** `FormatDefect::ExtTooLarge { len }` is now emitted on both sides when `ext_len > EXT_LEN_MAX`. Previously the writer emitted `ExtTooLarge` and the reader emitted the generic `MalformedHeader` for the same wire-format violation. Existing `match` arms on `MalformedHeader` for the specific `ext_len > EXT_LEN_MAX` case must be updated to `ExtTooLarge { len }`. Other reader-side `MalformedHeader` cases (truncation, malformed flags, length-field inconsistency) are unchanged.
- **Encrypt vs. decrypt routing uses magic-byte detection only** — file extension no longer forces a path. Files that start with the FerroCrypt magic but have a corrupted header now fail closed with a typed format error instead of being silently re-encrypted.
- **Atomic output handling.** Encrypted files and generated key files are staged under temporary names and promoted to their final path only on success; ordinary single-writer use no longer silently replaces an existing file. Directory decryption uses an `.incomplete` working directory that is moved into place once extraction finishes; on failure the staged tree is removed by default (see "Default cleanup-on-error" below) or retained when the caller opts in via `IncompleteOutputPolicy::RetainOnError`. Directory extraction uses the unified hardened extractor described above before promotion. The library contains no unsafe code.
- **Default cleanup-on-error for failed decrypts.** When a decrypt fails mid-stream — payload AEAD on a later chunk, archive structural reject after some entries were written, trailing zero-block reject, final-rename collision — the staged `.incomplete` plaintext is now best-effort removed before the typed `CryptoError` returns. Earlier revisions left the staged tree on disk, which surprised callers who expected "decrypt failed" to mean "no plaintext written" and could expose authenticated-but-incomplete plaintext to downstream automation. The retain-for-inspection behaviour is still available as `IncompleteOutputPolicy::RetainOnError` (CLI `--keep-partial`); callers who opt in MUST treat retained partials as a potentially attacker-chosen prefix because FerroCrypt's STREAM-BE32 payload only detects truncation when the final chunk arrives. Cleanup tracks only roots THIS run created, so a pre-existing `.incomplete` from a prior failed run is preserved across a retry that fails with `Previous .incomplete exists`.
- **File and directory permissions are preserved** through encrypt/decrypt round-trips on Unix. Setuid, setgid, and sticky bits are stripped on both archiving and extraction. Decrypted regular files are no longer marked executable. On non-Unix platforms, permission handling is platform-limited.
- **Breaking (library API): `ProgressEvent` split for accurate UI signalling.** The single legacy `DerivingKey` variant (which fired both for "Argon2id is about to run" and speculatively from the orchestrator before the file was even parsed) is replaced by two specific variants emitted at the actual KDF call boundary: `DerivingPassphraseWrapKey` (Display: `"Deriving passphrase key…"`) for the passphrase recipient encrypt + decrypt, and `UnlockingPrivateKey` (Display: `"Unlocking private key…"`) for `private.key` Argon2id unlock. Pure-X25519 encrypt and structurally-malformed file rejects fire **zero** KDF events. The orchestrator no longer emits a speculative event before parsing; UIs that previously showed "Deriving key…" briefly during X25519 wrapping or for the few microseconds before a malformed-file rejection no longer do. `match`/`matches!` on `ProgressEvent::DerivingKey` must be replaced with the specific variants. `DerivingPassphraseWrapKey` fires exactly once on a successful passphrase encrypt or decrypt and zero times when no passphrase slot is reached.

### Removed
- **Breaking: removed the public `fast-kdf` Cargo feature.** Earlier revisions exposed a Cargo feature that lowered `KdfParams::default()` to test-speed Argon2id parameters when any consumer in the dependency graph activated it. `KdfParams::default()` now always returns production parameters (1 GiB memory, time_cost 4, parallelism 4). Callers that genuinely need different parameters construct `KdfParams` explicitly and pass it via the new `Encryptor::kdf_params(...)` / `KeyPairGenerator::kdf_params(...)` builders.
- **Breaking (library API):** Removed the legacy `symmetric_encrypt` / `symmetric_decrypt` / `hybrid_encrypt` / `hybrid_decrypt` free functions and their `*Config` structs, the auto-routing wrappers (`symmetric_auto` / `hybrid_auto`), and the free functions `public_key_fingerprint` / `encode_recipient` / `encode_recipient_from_bytes`. Use `Encryptor` / `Decryptor`, `generate_key_pair(output_dir, passphrase, on_event)`, `probe_recipient_mode`, and `PublicKey` methods. `decode_recipient_string` remains as the low-level Bech32 primitive.
- `openssl`, `reed-solomon-simd`, `bincode`, and `serde` dependencies.
- **`tar` crate dependency.** Replaced by the in-tree FerroCrypt Archive (FCA) writer/reader; the entire transitive supply-chain pulled by `tar` (including `xattr` and platform-specific extension support) is gone. See the "Native FerroCrypt Archive (FCA) format" entry under **Changed**.

### Fixed
- **Decryption errors are now distinct and user-readable.** Previously a failed decryption surfaced as a wrapped internal error with no way to tell whether the password was wrong, the header was tampered, the payload was corrupted, or the file was truncated. The library now exposes a typed taxonomy:
    - `KeyFileUnlockFailed` — `private.key` failed to unlock (wrong passphrase or tampered file; the AEAD primitive cannot distinguish the two).
    - `RecipientUnwrapFailed { type_name }` — recipient body failed to unwrap (wrong credential or tampered body).
    - `HeaderMacFailedAfterUnwrap { type_name }` — multi-recipient: a candidate slot unwrapped but MAC verification failed; the loop continues to the next supported slot.
    - `HeaderTampered` — single-recipient: unwrap succeeded but MAC verification failed.
    - `NoSupportedRecipient` — no entry in the recipient list yielded a verifying credential.
    - `IncompatibleRecipients { type_name, policy }` — the file declares an exclusive recipient (today only `argon2id`) alongside any other entry; rejected before any KDF runs.
    - `UnknownCriticalRecipient { type_name }` — the file declares a recipient with the critical bit whose `type_name` is unknown to this implementation.
    - `PayloadTampered` — a ciphertext chunk failed authentication.
    - `PayloadTruncated` — the encrypted stream ends before its final-flag chunk.
    - `ExtraDataAfterPayload` — bytes remain after the final-flag chunk.
    - `KdfResourceCapExceeded { mem_cost_kib, local_cap_kib }` — KDF parameters request more memory than the configured limit allows.
    - `DecryptorModeMismatch { expected, found }` — wrong decryptor variant for the file's recipient list.

  Variants carry typed structured data so callers can pattern-match without parsing messages. Header-read I/O errors are more precise: a non-EOF `io::Error` (`PermissionDenied`, `BrokenPipe`, etc.) raised mid-header now surfaces as a real I/O error instead of being collapsed to a corrupt-file diagnostic — a failing disk no longer masquerades as a corrupted file. The CLI prints errors using `Display` instead of the default `Debug` format, so users see the library's short messages directly.
- **Security: Windows no longer silently overwrites existing output.** Earlier versions on Windows could replace an existing `.fcr` file or key file at the output path without asking. Encryption and key generation now avoid silently replacing existing final files, and directory decryption follows the same intent.
- **Security: archive payload conforms to the strict FCA wire format** (`FORMAT.md` §9). Hostile or malformed archive entries are rejected per a tight whitelist (entry kinds, path grammar, single top-level root, parent-presence, exact and ASCII-case-insensitive duplicate detection, declared total bytes equality) before any filesystem write — see the "Native FerroCrypt Archive (FCA) format" entry under **Changed** for the migration that removed the previous restricted POSIX ustar subset.
- **Security: an `x25519` recipient slot whose ECDH shared secret is all zero now causes file-fatal rejection in every code path** (`FORMAT.md` §2.4 / §4.2). Practical impact today is bounded — FerroCrypt's own writer cannot produce such files — but a structurally valid file from any source is now refused as required, regardless of recipient slot ordering.
- **Security: extraction rejects archives with multiple top-level roots.** FerroCrypt's archiver always produces exactly one. Earlier extraction silently created every root in a tampered payload while the public return value only reported the first; now any second distinct top-level root is refused before its output is written.
- **Security: key generation writes the public key before the private key.** If generation is interrupted partway, the private key never appears on disk — only an orphan public key remains, which is harmless.
- **Security: directory encryption no longer follows symlinks.** Symlink inputs and symlink entries inside directories are rejected before any Argon2id work runs. Hardlinks are archived as regular file contents. Extraction rejects unsupported file kinds (FIFOs, sockets, devices) instead of silently dropping them.
- **Security: extraction is hardened against local symlink/directory-component races across Linux, macOS, and Windows.** A concurrent local attacker who swaps a directory component for a symlink can no longer redirect writes outside the destination tree; on Windows, NTFS reparse points such as junctions and mount points are rejected too. The old path-based extraction fallback is removed.
- **Security: KDF parameters from untrusted headers are bounded** in every dimension (memory, time cost, parallelism), preventing denial-of-service via crafted encrypted files or key files. Over-budget headers surface as `KdfResourceCapExceeded` before Argon2id runs.
- **Security: native recipient entries with the critical bit set now reject before any expensive KDF work.** End behaviour is unchanged (the file is still rejected); the rejection happens earlier so an adversarial file cannot force compute on a CPU/RAM-bounded reader. FerroCrypt's own writers cannot produce such entries, so files written by any FerroCrypt release are unaffected.
- **Security: plaintext and key material are zeroized after use** — per-chunk plaintext buffers between chunks and on drop, decrypted key material in zeroizing wrappers, covering success, error, and unwinding paths.
- **Desktop: worker thread panics no longer freeze the UI.** Previously, a panic in the encrypt/decrypt/keygen worker (e.g. Argon2id OOM on a constrained host) left the UI permanently disabled with the "working…" state stuck. The app now stays recoverable on panic.
- **Recipient-decrypt progress phases.** The recipient (X25519) decrypt path now emits `UnlockingPrivateKey` before the private-key Argon2id runs and `Decrypting` only after the recipient body unwraps — matching the passphrase path's `DerivingPassphraseWrapKey` → `Decrypting` ordering. Previously a UI mislabelled the multi-second KDF window as "decrypting".
- **Pub/priv key file mix-ups now report `WrongKeyFileType`.** Previously, reading a binary `private.key` as a public key surfaced a cryptic UTF-8 error, and reading a text `public.key` as a private key surfaced a generic format defect.
- **`public.key` enforces strict canonical whitespace.** The file MUST be the lowercase `fcr1…` recipient string optionally followed by exactly one trailing `\n`. Other surrounding whitespace (CRLF line endings, leading blanks, trailing spaces, blank lines) is rejected as `MalformedPublicKey` rather than silently trimmed.
- **Missing key-file paths** surface as a typed input-path error instead of leaking a raw OS error string.
- **`InvalidKdfParams` Display wording.** "File has invalid decrypt settings" → "File has invalid KDF settings": neutral across the encrypt/decrypt split.
- Output-conflict wording unified to "Output already exists: `path`". Symlink-race wording unified to "Input is a symlink: `path`".
- **Re-running encrypt against an existing output now fails immediately**, before any Argon2id derivation runs. Previously a populated destination cost a multi-second KDF in passphrase mode before the conflict surfaced. The atomic no-clobber rename remains the load-bearing race-proof guarantee. The same preflight catches dangling symlinks at the destination — earlier versions used `Path::exists()`, which follows the link and returned `false` for a missing target, letting the KDF run before the rename eventually refused to overwrite.
- **Recipient strings with non-ASCII characters now reject with a clear `InvalidInput("Recipient string must be ASCII Bech32")`** instead of misclassifying as a length-cap exceedance. Bech32 (BIP 173) is an ASCII-only grammar.
- Crash on truncated, corrupted, or maliciously crafted `.fcr` files replaced with structured format errors.
- Default encrypted output naming for directories with dots (e.g. `photos.v1/`) preserves the full directory name (`photos.v1.fcr` instead of `photos.fcr`).
- Nonexistent input paths no longer silently produce empty encrypted files.
- `keygen` creates missing output directories. Key pair generation is atomic: both files are written to temp names, `fsync`'d, and renamed into place; partial state is cleaned up on failure.
- Directory archiver no longer silently skips inaccessible files or path errors.
